# Performance scorecard

Every iteration should show what improved and what regressed. A run writes one `chalk.scorecard/v1` file per media plane, and `scorecard diff` compares it with a baseline using the budgets in `perf/budgets.json`. `schema.mjs` owns the shape and the metric registry (`METRICS`, one unit per id). `scorecard.mjs build --help`-style flags and the input adapters in `adapters/` define which report becomes which metrics. A scorecard uses `chalk_sfu` as its plane when the metrics do not depend on one, such as bundle sizes.

## Budgets

`perf/budgets.json` is the only budget file: `_comment` records one reason per change, `callRun` holds the web call check settings, and `budgets` maps a metric id to `{ max_p50?, max_p95?, min_p50?, tolerancePct, gate }`. Pass-rate metrics use `min_p50` because higher is better. `gate: true` fails a result over the limit; every budget gates, and the checks register (`scripts/gates/check-register.mjs`) fails on an entry with `gate: false`. A metric from a real node gates from the start with a loose ceiling (twice the worst early p95) and tightens in its own pull request once seven nightly values from at least three nights have a run-to-run spread below `tolerancePct`; a metric nothing produces gets no entry. See [the budget doc](../../docs/performance-budget.md#changing-a-budget).

`scorecard.mjs diff --current a.json --baseline b.json` prints ❌ for over budget, ⚠️ for worse than `tolerancePct` against the baseline but within budget, and ✅ for more than 5% better. With `--fail-on-gate`, only a ❌ on a gated entry fails.

## Tiers

- **Pull request.** `pr-tier.sh` runs inside the existing Gate jobs and adds no job. It scores call bundle sizes and the SFU loopback test against the latest successful master push (`scorecard-web` and `scorecard-sfu` artifacts) and updates one sticky comment.
- **Nightly.** `nightly.sh` runs in the `scorecard` job of `Cut nightly` (with `SCORECARD_KEEP_ISSUE=true`, so only the latency workflow's full card closes the regression issue) and in `.github/workflows/nightly-latency.yml`, even when the cut fails or is held. It compares the run's `chalk_sfu` latency card with the median of the last seven nightly runs, appends to `history.jsonl` on the `scorecard-history` branch, regenerates the trends file, and keeps one open `Scorecard regression` issue while a gated metric is over budget. Nightly measures a throwaway Chalk SFU, never the production node.
- **Nightly gate.** The cut's proof lanes run on throwaway stacks (`scripts/nightly-stack`); one is a latency smoke (`pnpm prod:latency --smoke`) that runs a few cycles and fails when a gated `chalk_sfu.action.*` metric is missing, short or timed out, but does not gate speed, because a shared runner's CPU says nothing about it. `.github/workflows/nightly-latency.yml` runs the full `pnpm prod:latency --planes chalk_sfu` for the newest held cut that has no covering record, against a Chalk SFU on a host created for the run, and records its verdict for that SHA. Promote needs a covering record only when the diff since production touches a latency path (`release.py latency_paths`). A failed latency run, a missing record, a gated `chalk_sfu.action.*` p95 over its ceiling, or a missing or empty card blocks promotion without touching the release record. `evaluate.mjs` reads `perf/budgets.json` from the scored SHA with `git show` and saves a SHA-and-run-bound `passed`, `gated-breach` or `missing` verdict. Every gated `chalk_sfu.action.*` metric is required evidence, so a card that lacks one with samples is `missing`, never a pass. A Cloudflare card alone cannot replace a missing Chalk SFU card.
- **Cloudflare latency.** `.github/workflows/nightly-cf-latency.yml` runs the same kit on `cf_sfu` after a successful `Cut nightly`. It holds neither the nightly environment lock nor any cut job, so it cannot delay a cut or change the conclusion the Android release reads. Its card uploads as `warn-scorecard-nightly-cf_sfu` (which the gate's `scorecard-nightly-*` download never matches), and `SCORECARD_WARN_ONLY=true` stops `nightly.sh` from touching the regression issue. Every `cf_sfu` budget gates, but only its own run: a breach turns the `latency` job red, so that night records no history card, and blocks nothing else. The limits are interim because the workflow has run only three times. `nightly-graph.test.mjs` and `cf-sfu-card.test.mjs` pin this. Every place that shows the card also shows `plane-note.mjs`, because the two planes are not yet a fair comparison from the CI region.
- **Promote.** After the production proof passes, the Leave run is scored against the nightly median. These jobs run only after `proof` and nothing needs them, so a failure cannot start `rollback`. A gated breach triggers one rerun of the Leave proof, and `scorecard-final` fails only if the rerun still breaches, then opens or updates the regression issue. Promote checks the nightly Chalk SFU proof and scorecard verdicts at selection and approval recheck. `scorecard_override` takes a written reason (non-empty) to accept failed, skipped or missing proof, gated breaches or missing evidence, and records it in the run summary and release record. SHA mismatches and invalid release artifacts still block.

## Latency diagnostics

The latency kit also writes `latency-diagnostics-<plane>.json` next to the card. It is a sidecar, never in the card, because readers that shipped earlier reject a card with an unknown field. The gate, diff, history and baseline never open it; only the `chalk-sfu.mjs` run summary reads it, and a missing or invalid sidecar becomes one line of text (`diagnostics.test.mjs` pins this). `perf/budgets.json` has no entries for it.

- `rtt.sfu_ms` and `rtt.sync_ms` show distance from the runner to the plane under test. The kit sends nothing on the Sync socket, so it cannot disturb the SDK's liveness checks.
- `stages` (named in `stages.mjs`) splits each action into pieces between wire events. A stage counts from the last stage reached, so a step the SDK skips is null and its time moves to the next one. Retired stage ids stay valid in older sidecars (`RETIRED_STAGE_IDS`).
- `audio` holds `media.network_jitter_one_way_ms`, an estimate from the listener's WebRTC stats: half of each guest's SFU round trip plus the jitter buffer's average wait. It assumes a symmetric path, is not mouth to ear, and lives only in the sidecar.
- `ice` records the selected candidate pair type and request/response counters of the joining guest, read after the join's measured stages and never inside a measured interval. Requests far above responses on the winning pair mean early ICE checks were lost, and `relay` means TURN carries the media. No address or candidate id is kept.
- `path` and `ice.relay_protocol` come from `--path` (see [prod-proof](../../scripts/prod-proof/README.md)): the mode, whether the joining guest connected, and the loss share and jitter it received over the call. `ice.relay_protocol` is `udp`, `tcp` or `tls` when the selected pair is a relay.
- Both guests run on one host, so readings use `performance.timeOrigin + performance.now()`. `scripts/prod-proof/latency-trace.mjs` is an init script only the latency kit installs; the product SDK carries no trace code, and a failed trace read nulls that action's stage fields without dropping the cycle.

## Contention on the shared Nightly host

The full Chalk SFU latency run owns its host, so it has nothing to contend with. Measurements that still use the shared Nightly host (the Cloudflare latency run) run under the Git-ref lease in the [SFU lane protocol](../media/sfu/README.md#shared-staging-node). Only nightly's Chalk SFU caller grants `contents:write`; a direct staging dispatch without write access fails closed at lease acquisition. Cleanup by run ID always runs without the lease, so a busy lease never strands Episodes or Spaces, and any deletion failure fails the job. Lease labels and times are public, so use non-sensitive labels.

The measurement reads API-log windows before and after the kit (`staging-logs.mjs` owns the dataset configuration, with `CHALK_AXIOM_STAGING_LOG_DATASET` and the read-only `CHALK_AXIOM_QUERY_TOKEN`). It counts distinct foreign Episode and provider-session IDs and excludes its own by `episode_id`. Node gauges (`staging-metrics.mjs`) come from a second read-only Axiom source via `CHALK_AXIOM_STAGING_METRICS_DATASET`, `CHALK_AXIOM_METRICS_BASE_URL` and the `CHALK_AXIOM_METRICS_QUERY_TOKEN` secret, which only the latency step sees and the kit's own environment never does. Public cards hold counts only, never Episode or connection IDs, dataset names or incarnation IDs.

The optional `contention` block records each signal as `{ value, source }`. Missing tokens, failed queries and incomplete responses leave signals `"unavailable"`, never zero, and node coverage in all three phases is required, so unavailable steal cannot yield an isolated card. A successful query with no `chalk_sfu` events sets `zero_chalk_sfu_events.value: true`, which may mean an idle node or a logging gap. The collector rejects responses reaching its conservative 1,000-point or 1,000-series policy cap, which is not a claimed endpoint limit. Quiet API logs do not prove an already-connected silent foreign session is absent, so boundary session gauges add a check.

Partial log windows, no own-Episode coverage, a lost lease, or observed foreign Episodes make a card `contended: true`. After a contended attempt the job waits for a quiet window and retries once under the lease, never adding load while the pre-measurement window is busy. Both attempts stay in encrypted evidence and only the final card is published. A contended final card is labelled in summaries, fails the measurement job, stays in history for diagnosis, and is excluded from baselines and trends. It never opens a regression issue and cannot close one as though clean. Budgets are unchanged.
