flow A · the join, isolated browser path

A browser joins a room

This is what happens between a person opening a room link and their video reaching everyone else, traced through the code as it runs today. Seven stages. The short version: the web app's local backend admits the participant and hands the browser its credentials, then the SDK raises two arms in parallel, a Sync WebSocket for state and a WebRTC connection for media, and calls itself live only when both are up. Every claim below was verified against source on 2026-08-01.

or open any stage on its own

The room route calls createLocalBrowserSession(displayName, inviteToken) against the app's own small backend (a BFF, backend-for-frontend), which binds the browser to a server-side session with a same-origin cookie. The BFF creates the room and meeting session if they don't exist yet, then admits the participant through the server SDK.

The API's admission handler does the heavy lifting: it records the participant's lifecycle intent, provisions a Cloudflare SFU connection server-to-server, and returns the access bundle in one response: participant identity, a generation counter, the Sync WebSocket URL with a five-minute JWT, and the Cloudflare bootstrap (connectionId, STUN server). The browser never talks to Cloudflare's control API directly.

ChalkSession.join() is careful about repeat calls: while joining it returns the in-flight promise, while live it resolves immediately, and from any other state it rejects. A fresh join resets state, increments an epoch counter (so stale async results from an abandoned join are discarded), and transitions idle → joining.

Its first act is media capture: getUserMedia runs before credentials are even initialized, so the permission prompt is the first thing a person sees. If both microphone and camera start disabled, the SDK skips the device API and uses an empty stream.

Worth knowing: the stock React meeting room fires join() in a mount effect and deliberately discards its rejection. A failed join is visible only through the session snapshot and connection overlay, never as a thrown error in the embedding app.

access.initialize() validates the bundle from A1. The access manager owns credential freshness from here on: it schedules a refresh 60 seconds before expiry, deduplicates concurrent refreshes, and rejects an unexpected connection replacement.

Then the production dependency factory builds a CloudflareSFUClient (with callbacks for fresh media tokens and for replacing a dormant connection) and a V3SyncClient that shares the same access bundle. Whiteboard and chat-file transports are separate adapters. Both clients start inside one Promise.all, so from this point the media branch and the Sync branch run in parallel.

The client upgrades a WebSocket to /v3/sync and sends a hello frame carrying protocol version 3, the Sync JWT, its control/media/presence cursors, and the room-actions extension cursor. The server verifies the token, applies the participant's admission intent to the Stateholder (the durable state authority), negotiates room actions, and begins recovery: it replays the control, media, and presence projections from the client's cursors forward.

The client considers Sync live only after control recovery plus both projections are complete. From then on, control events arrive strictly in revision order and the client sends a delivery_ack after applying each one. The reducer is where room state takes shape: participant_joined appends a participant, participant_left removes one, session_ended marks the meeting over.

The media client prepares the captured tracks and, for each one, adds a sendonly transceiver, creates and sets a local SDP offer, and posts it to Chalk's own signaling route. The API authorizes the media bearer token, forwards the offer to Cloudflare's /tracks/new, records the publication in a server-side registry, and hands the SFU's SDP answer back.

Two guards matter here. The client waits up to 8 seconds for the PeerConnection to become live before confirming anything. And it refuses to treat a publication as real unless the response carries the registry's authoritative publication ID: an SDP success without an identity is an error, not a degraded state.

Once its own tracks are live, the client polls the publication registry every 1,000 ms for enabled remote publications. Each newly discovered one triggers a pull: a remote-track request on the same signaling route, an optional renegotiation when Cloudflare answers with an immediate offer, and then a wait of up to 5 seconds for each actual RTCTrackEvent to arrive. The resulting tracks land in the remote projection that React renders as participant tiles.

Discovery is deliberately doubled: Sync separately observes the media plane server-side and projects media/presence state into its own stream. A subscriber can learn about a publication from either path; the registry poll is the authoritative one for actually pulling tracks.

The session never publishes live because a WebSocket said welcome or because an SDP answer arrived. The parallel start from A3 resolves only when the media client is live and Sync has finished recovery, and the same double condition guards every later return to live after a wobble. The Sync wait has a 10-second startup budget; blowing it fails the join.

The transition records a state_changed diagnostic and publishes a new immutable snapshot. React hooks consume these through useSyncExternalStore, so everything the UI shows, participants, tracks, chat, connection state, is a render of the latest snapshot rather than a stitched-together event stream.

flow B · the full meeting create → end

The life of a meeting

The join is one chapter. A meeting also has to be created, announced to the people already in it, controlled, dropped and recovered, left, and cleaned up after. Eight stages, from the first API call to the last webhook.

or open any stage on its own

Rooms and meeting sessions are separate resources: the room is the durable place, the session is one meeting inside it. The backend creates an active room pinned to the Cloudflare media plane, then a session with open admission, host-exit transfer, capabilities, a one-hour maximum duration, and an idempotency key so a retried create can't double-book. The API applies the max-duration deadline at creation time.

server → apiPOST /v1/tenants/{t}/rooms status: "active", media_plane: "cf_sfu"
server → apiPOST …/rooms/{r}/sessions open admission, capabilities, 1 h max, idempotent
apps/web/scripts/local-chalk-backend.mjs:162-192 the payloads the local backend sends apps/api/internal/httpapi/rooms.go:202-224 room creation handler apps/api/internal/httpapi/session_lifecycle.go:231-265 session creation + max-duration deadline

Nothing special distinguishes the first join except an empty room on arrival. Admission records the lifecycle intent and provisions the Cloudflare connection, and the browser walks Flow A exactly as traced above. The one structural point worth holding onto: joining is a durable server-side operation from the first moment, not a client-side handshake, which is what makes everything downstream (discovery, recovery, cleanup) replayable.

Existing participants don't learn about a newcomer from a client broadcast. A server-side lifecycle consumer polls pending admission intents every 100 ms and applies each through the Stateholder, which persists the control transition and commits a receipt. The Coordinator then publishes participant_joined to every connected socket; each client's reducer appends the participant and preserves host derivation. A client that was disconnected at that moment gets the same event later through cursor recovery, so nobody can permanently miss a join.

The newcomer's video is a separate concern on a separate path: their publication lands in the media registry (A5) and reaches subscribers through the 1-second poll (A6), plus Sync's own media projection. Presence and media can therefore briefly disagree, by design.

Publishing is the A5 offer chain; subscribing is the A6 pull. The registry in between is what keeps them honest: a publication exists only once the API has recorded it with an authoritative ID, and subscribers only pull publications the registry reports as enabled. All SDP work on a client is serialized through one queue, which prevents concurrent negotiation races but also means one stuck signaling request holds up every negotiation behind it.

Toggling a microphone is not a local flag flip. The session serializes commands per source, captures a device track first if enabling, then sends a durable live_target frame over Sync. The server routes it through the live session and provider bridge, applies the grant or revoke as a provider operation, and returns the result; only then does the client touch WebRTC, replacing the sender's track with null to mute or republishing to unmute. The whole exchange has a 15-second deadline with up to 16 server delivery retries and 3 local media retries.

Screenshare follows the same shape with getDisplayMedia in front, and its stop path is deliberately server-first: disable over Sync, then clear the local track. One deliberate quirk to hold onto for the watchlist: muting never calls the provider's closeTracks route, even though the whole chain for it exists server-side.

Chat and reactions are room actions on the Sync socket, negotiated during the hello. A sent message appears locally as pending, is confirmed or marked failed by the server, and history pages in over the same channel whenever Sync is live. Attachments are plain authenticated HTTP: initiate an upload, finalize it, download by ID.

The whiteboard is its own authenticated WebSocket at /v1/whiteboard, with its own welcome, snapshot recovery, heartbeat, and multipart reassembly, fanned out independently of the control stream. Recording is wired through the protocol and the server's operation workers, but the public session action surface doesn't expose it yet, so no browser button reaches it.

Recovery is layered, and the layers have different temperaments. When the Sync socket drops, the client clears its media and presence projections, rejects everything ephemeral (directed requests, room actions, in-flight live targets), keeps durable commands for replay, and reconnects after 250 ms, with no attempt cap at that layer. Heartbeats run every 20 seconds on both sides; the server closes after 2 misses, the client after more than 2.

Above it, ChalkSession shows reconnecting and runs a bounded loop: three attempts inside a 10-second budget with 100/250/500 ms backoff, then failed, permanently, until a fresh join(). Media recovery inside that loop refreshes access with a replacement Cloudflare connection, restarts the SFU client, and then waits for Sync to be live, so Sync trouble can burn the media budget even when the SFU is healthy.

leave() transitions to leaving, sends a durable participant_leave operation, waits up to 5 seconds for confirmation, then stops Sync and media, releases device tracks, clears access, and lands on left. The server side is idempotent by operation key, so a retried leave can't remove someone twice. The web app adds a second, independent cleanup trigger: its backend route ends the session for a host or removes a non-host, while a route unmount separately queues session.leave(). Two coded paths, one intent.

Ending the meeting is heavier. end_session locks active participants and recordings, applies end fences, and hands cleanup to the external-operation worker, which runs media and recording cleanup in parallel and confirms the end only when every child confirms (up to 100 attempts with capped exponential backoff). The Stateholder then marks participants complete and the session ended, and webhook production inserts versioned events with queued deliveries. A browser closing its socket proves nothing about any of this; completion is a database-backed operation result.

Where this can break

A full audit of these flows found 37 concrete behaviors worth supervising: timeouts, retry policies, race windows, and silent failure paths, each tied to current source. These are the ones to watch first. Everything here is verified code behavior, not hypothesis; the complete audit sits beside this document in meeting-lifecycle-trace-codex-2026-08-01.md.

Join failures are invisible to the embedding app

fix before prod

The stock React meeting room calls void actions.join().catch(() => undefined), so a join outage surfaces as a hung overlay and nothing else: no thrown error, nothing an embedding app can log or alert on. Failure state exists in the snapshot, but nobody is forced to look at it.

sdks/typescript/react/src/components/full/SessionMeetingRoom.tsx:45-49 · stage A2

Core signaling fetches have no timeout

fix before prod

The SFU transport and the server SDK transport both call fetch with no AbortController. The session's timeout wrapper stops waiting but can't cancel the request, and since all SDP work is serialized through one queue, a single hung signaling call blocks every negotiation behind it for as long as the network lets it hang.

media/transport.ts:20-66 · server/transport.ts:88-99 · media/client.ts:301-315 · stages A5, B4

Mute never closes the provider publication

verify in prod

Muting only calls replaceTrack(null) and clears local state. The full closeTracks chain exists through the API and the Cloudflare adapter, but nothing in the media client calls it, so the registry or provider may keep a stale, enabled-looking publication after a mute. Whether that costs anything in production is exactly the thing to verify.

media/client.ts:282-299 · sfu_signaling.go:157-226 · stage B5

Publication polling fails silently, forever

watch

The 1-second registry poll catches every error and just schedules the next poll, with no failure count and no escalation. If the publications endpoint breaks, an in-call participant simply never sees new people's media while everything else looks healthy. Worth a server-side alert on that endpoint's error rate.

media/client.ts:578-589 · stage A6

Camera permission is requested before credentials

watch

Capture runs before access.initialize(), and neither the permission prompt nor the device acquisition has any timeout. A person can grant camera access and then sit at a spinner while the access request fails behind it; track cleanup then depends entirely on the join catch path.

chalk-session.ts:386-392, 441-450 · stage A2

Recovery gives up after 10 seconds and 3 attempts

watch

That budget is shared: media recovery refreshes access, restarts the SFU client, and then waits on Sync, so a slow Sync tier can exhaust the whole budget while media is fine, landing the session on a permanent failed that only a fresh join() escapes. Any blip longer than ten seconds ends every affected session.

chalk-session.ts:39-43, 848-919 · stage B7

Tokens live five minutes, refresh failures retry quietly

watch

Sync JWTs expire after 300 seconds; refresh is scheduled 60 seconds early and a failed refresh just retries every 5 seconds as a diagnostic, without ever escalating the session state while it stays live. A reconnect delayed near expiry, or clock skew beyond the verifier's 30-second allowance, is a real failure path.

synctokens/service.go:21-29 · access-manager.ts:45-60 · chalk-session.ts:921-935 · stage A3

Heartbeat thresholds differ by one

watch

Both sides check every 20 seconds, but the server closes after 2 missed heartbeats while the client waits for more than 2. The server will usually win that race, which is survivable but is the kind of asymmetry protocol tests should pin down before it drifts further.

socket_v3.ex:23-25 · v3-client.ts:1437-1449 · stage B7

End cleanup and webhooks need their own monitoring

watch

A meeting's end is confirmed only when every media and recording cleanup child confirms, with attempt 100 becoming a terminal failure; separately, the webhook production summary query has a 1-second timeout whose failure is silently ignored. Neither is visible from any browser, so production needs alerts on terminal external operations and on that query.

external_operation_consumer.ex:320-367 · stateholder/postgres.ex:4459-4475 · stage B8

What already looks sound

solid

The load-bearing invariants hold up under reading: live requires both Sync and media to be live, a publication doesn't exist without an authoritative registry ID, lifecycle operations are durable and idempotent by operation key, controls are two-phase with the server authorizing first, and missed events replay through cursor recovery so a disconnect can't permanently lose a join or a leave.

vocabulary shared language

The words the code uses

BFF

The web app's own small backend (backend-for-frontend). It holds the server API key, admits participants, and hands the browser only its personal credentials.

access bundle

The admission response: participant identity, generation counter, Sync URL and JWT, and the Cloudflare bootstrap. Everything a browser needs to raise both arms.

Sync (v3)

The WebSocket protocol carrying room state: control events, presence, media projections, live targets, and room actions, all ordered by revision and resumable by cursor.

Stateholder

The server-side durable authority for room state. Lifecycle intents become committed transitions here before any client hears about them.

Coordinator

The Sync server process that publishes committed events to connected sockets and replays them during recovery.

SFU

Selective forwarding unit: the media server (Cloudflare's, here) that receives each participant's tracks once and forwards them to everyone else.

publication

A track registered in the API's media registry with an authoritative ID. Subscribers discover and pull publications, never raw tracks.

live target

A durable Sync frame expressing a desired media state (mic on, camera off, screen shared). The server authorizes it, then the client applies it locally.

room action

The ephemeral message family on the Sync socket: chat, reactions, read receipts. Rejected on disconnect rather than replayed.

cursor recovery

Reconnection by position: the client presents its last-seen cursors and the server replays everything after them, so missed events arrive late instead of never.

external operation

Durable server-side work (cleanup, recording, provider calls) run by a worker with bounded retries. Confirmed results live in the database, not in any socket.

snapshot

The immutable state object ChalkSession publishes after every change. React renders snapshots via useSyncExternalStore instead of stitching events.

epoch

A counter incremented on each join attempt so async results from an abandoned attempt are recognized as stale and discarded.

generation

A server-issued counter in the participant's credentials that distinguishes successive admissions of the same participant.
