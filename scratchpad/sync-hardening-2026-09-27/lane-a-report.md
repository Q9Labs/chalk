# Lane A — Sync and media control-path map and tool audit

**Date:** 2026-09-27  
**Scope:** Read-only source audit and safe help/usage probes. No production or deployed service was contacted. “Participant,” “Space,” and “Episode” follow `GLOSSARY.md`; “participant” in code/wire names is retained where applicable.

## Evidence labels

- **Verified by reading code** means the cited implementation directly shows the behavior.
- **Observed by invocation** means the exact command/result appears in section 4.
- **Inference / suspected** means a consequence of the shown ordering/timeouts that was not reproduced in a running system.
- No latency measurements or production topology were available, so this report does not attribute the observed >1s symptom to a component.

## 1) Toggle path

The microphone and camera share the same generic `MediaController.#set` pipeline; only the source, capture constraints, and Sync method differ. The important ordering is: **local capture/prepare on enable → Sync live-target request → server-side provider operation/reconciliation → result to browser → local WebRTC publication work → final controller state**. Disable skips capture, but on the server it may close active SFU tracks before the browser removes its local sender track.

### Explicit answers

- **Does the Sync reply to `set_microphone_enabled` wait for a Cloudflare API call?** The Sync `live_target_result` does **not** wait for Cloudflare on enable: the server-side grant is authorization/receipt work; the browser performs SFU signaling only after it receives the Sync result. On disable, Sync waits for the API bridge; if active publications exist, the API executor waits for Cloudflare `CloseTracks` before returning. If no publication exists, it may satisfy without that Cloudflare call. Camera uses the same path.
- **Does it wait for a synchronous-standby commit?** Enable waits for its Sync grant-reservation and grant-completion Postgres transactions, which set `synchronous_commit=on`. Nonlocal runtime defaults to requiring a synchronous standby at boot (`apps/sync/config/runtime.exs:363-377`); with a configured synchronous standby, these commits wait for its flush. The local default explicitly disables that requirement (`apps/sync/config/config.exs:17-18`). The deployed topology was not inspected. Mic/camera disable has no Sync-side grant write transaction. API database commits occur during bridge work, but their standby policy was not established here.
- **Does the UI update optimistically?** Pending/requesting state is published immediately. The UI does not mark enable as enabled until the Sync result **and** local media-port work succeed. For disable, the pending state maps to muted/off immediately, so the off visual is optimistic even though completion is pending.
- **Is there a sleep, debounce, or poll in the direct path?** No fixed sleep or debounce was found in the initiating toggle path. It can queue behind same-source and SDP serialization; it has retry timers. Background polling exists: Sync observation reconciliation (~2s), browser remote-publication discovery (1s), and coordinator durable-head repair (~5s). The configured 100ms external-operation worker poll is not a fixed pause inserted into this live media bridge path. The direct path also has bounded bridge/adapter/connection waits listed below.

### Timing, retries, locks, and network summary

- Sync ProviderBridge request budget: **7s**; one `MediaPlaneCall` adapter budget: **8s**; coordinator call timeout: **9s**. Confirmed results also perform an immediate observation GET, so the two bridge calls are sequential. A suspected edge is the 9s outer call expiring while the coordinator callback is still within its second adapter call; that can make outcome delivery ambiguous.
- Sync enable grant: two separate transactions, each outer-bounded to **3s**, lock timeout **750ms**, SQL statement timeout **2s**, and `synchronous_commit=on`. Authority read has **1s** query timeout. Durable command transactions use the same SQL transaction configuration/authority-lock family.
- Client live-target server retry budget: **15s**, 100ms base backoff capped at 1s, up to 16 retries. Local media retry: up to 3 attempts with 100ms base delay; no total local-call deadline after the server success clears the 15s timer.
- Browser WebRTC connection wait: **8s**, with 20ms predicate polling. Remote track arrival wait can be **5s**. Browser API fetch has no explicit abort timeout. Capture has no app-specific timeout.
- Network calls on critical path: browser↔Sync WebSocket request/result; Sync↔Postgres authority read and (enable only) reservation/completion transactions; Sync↔API bridge POST and confirmed-result observation GET; API↔Postgres provider receipt/observation operations; API→Cloudflare close on active disable, or browser→Chalk API addTracks→Cloudflare on enable; WebRTC signaling/connectivity and RTP path. The exact API Postgres transaction replication wait is unknown.

## 2) Sync correctness design and suspected risks

### Design in plain language

1. **Do not conflate durable control commands with live media targets.** The TypeScript `V1CommandScheduler.sendTarget` path persists durable command targets locally before sending, handles receipts/retries, and restores pending targets; `sendOperation` is transient (`sdks/typescript/client/src/sync/v1-command-scheduler.ts:112-174,303-312`). Mic/camera self-toggle uses `V1LiveTargetCoordinator` and a `live_target` frame instead. That live target is not an event in the durable command log and is cleared/rejected on disconnect (`v1-live-target-coordinator.ts:81-100,145-149`).
2. **A durable command is decided by Postgres, not an Episode process.** A live WebSocket `command` is validated and admitted through bounded per-Episode in-memory intake, then `Stateholder.Postgres.decide_command` executes a database transaction (`apps/sync/lib/chalk_sync/transport/socket.ex:346-369`; `apps/sync/lib/chalk_sync/episodes/command_intake.ex:23-52`; `apps/sync/lib/chalk_sync/stateholder/postgres.ex:37-62`). `CommandDecision.transaction` configures timeouts/synchronous commit, locks control/Episode/Participant authority rows, and checks the prior receipt (`command_decision.ex:30-49`; `sql/authority.ex:4-35`).
3. **The durable write is atomic.** For a new accepted command, one transaction inserts the event, updates product/control folded state and digest, inserts its committed receipt, then emits a Postgres notification hint (`command_persistence.ex:58-86`). Duplicate command IDs with matching fingerprint return the stored receipt; conflicting fingerprint is rejected. If the transaction result is uncertain, code looks up the receipt; unavailable/absent evidence returns retryable instead of inventing an ack (`command_decision.ex:17-28,174-180`).
4. **Episode coordinators are disposable delivery/fanout processes.** Their in-memory state holds socket/subscriber queues, not the authoritative durable control log (`episodes/coordinator.ex:1-7`). Notifications are hints; nodes catch up from Postgres in exact-next order and periodic repair rereads the durable head (around every 5s) (`episodes/coordinator.ex:22-25,473-493,572-604`).
5. **Reconnect is cursor-based recovery.** The client hello carries revision/schema/digest cursor (`sdks/typescript/client/src/sync/v1-client.ts:355-365`). A repeatable-read recovery transaction checks the cursor/head and returns no-op, exact replay, or canonical snapshot. Replay is bounded (up to 2,048 events / 2MiB); otherwise the server falls back to a snapshot (`apps/sync/lib/chalk_sync/stateholder/postgres/recovery_reader.ex:41-67,136-171,186-226`). The client validates/applies the frames, receives recovery-complete, then sends `recovery_ack` with recovery ID/revision/digest (`v1-client.ts:485-519,575-579`). The socket/coordinator validate that acknowledgement against the exact pending recovery/head and close on mismatch (`transport/socket.ex:322-344`; `episodes/coordinator.ex:387-404`).
6. **Node loss after durable command acknowledgement.** By code ordering, the state/event/receipt transaction commits before the command is acknowledged. If that Sync node then dies, its in-memory coordinator disappears, but a reconnecting client can recover from Postgres via replay or snapshot. Transaction settings request synchronous commit; nonlocal startup defaults to requiring a synchronous standby. This conclusion is verified from code ordering, conditional on Postgres honoring the configured synchronous-standby setup; the actual deployed failover topology was not inspected.
7. **Postgres unavailable.** Current nonlocal runtime chooses `Stateholder.Postgres` (`apps/sync/config/runtime.exs:262-266`); in-memory Stateholder is the local default only. A command decision/authority/recovery read returns retryable/unavailable rather than treating process memory as durable truth. Recovery hello can be rejected/retried (socket dependency failures close with retryable service-unavailable handling, `transport/socket.ex:273-281`); pending client commands retry when connection returns. No successful durable ack can be manufactured while the transaction/receipt is unavailable. Live targets also fail/retry because authority/reservation/provider calls cannot be completed.

### Risks and edge cases

| Status | Finding |
|---|---|
| **Verified by reading code; suspected user-visible consequence** | Live mic/camera targets are ephemeral: disconnect rejects/clears the in-flight client item rather than replaying it after recovery. A server-side grant/revoke may already have happened before the socket result was lost. The client can therefore see an ambiguous result; manual retry can issue a new operation ID. This does not weaken the separate durable command log, but it is a media-state reconciliation/idempotency risk. |
| **Verified by reading code; suspected timeout consequence** | The coordinator handles a live target synchronously and awaits provider work plus immediate reconcile. One adapter call is bounded to 8s, but the outer coordinator call is 9s and a confirmed result may trigger a second adapter call. It is plausible the outer caller times out while the coordinator is still executing; side-effect/result ambiguity or head-of-line blocking can follow. Not reproduced. |
| **Verified by reading code; suspected hang** | Once a successful Sync result arrives, the live-target coordinator clears the 15s server deadline before running local `ports.media`. The browser fetch used for SFU signaling has no explicit abort timeout. A stalled fetch can keep the local promise, controller pending flag, and UI busy state unresolved. Not reproduced. |
| **Verified by reading code; suspected temporary divergence** | Enable first records an authorization grant, then browser publication occurs after the Sync reply. If browser capture was prepared but the API/SFU signaling or local negotiation fails, Sync grant/intent and actual publication can temporarily disagree. For disable, provider close precedes local sender removal. Recovery/retry behavior reduces but does not eliminate an interval of divergence. |
| **Verified by reading code; suspected throughput impact** | The Episode GenServer serially performs the live target and follow-up reconciliation inside its callback. Slow bridge/API/Postgres calls can delay unrelated messages for that Episode. No queue-latency measurement was run. |
| **Verified by reading code; no defect confirmed** | Durable command admission is bounded, Postgres transactions serialize on authority locks, receipts are idempotent, and recovery validates exact revisions/digests. I found no code path that clearly loses, duplicates, or reorders an **acknowledged durable command**. This is a source review, not a proof that every crash/failover schedule is correct. |
| **Suspected / deployment-dependent** | An acknowledged transaction’s survival across a real primary promotion depends on the deployed synchronous-standby configuration and failover policy. The application asks for `synchronous_commit=on` and requires a standby in nonlocal startup, but deployed settings/health were intentionally not checked. |

## 3) Tool audit

### 3.1 `apps/sync/docs/reliability-harness.md` and referenced harnesses

**Claim.** The document says one harness owns Sync reliability: a PostgreSQL-backed correctness profile with zero skips, deterministic v1 breaker, TypeScript Sync and whiteboard tests; a topology profile with real Sync OS processes and primary/standby Postgres; and a release profile adding multi-node load, restart recovery, and real Chromium (`apps/sync/docs/reliability-harness.md:3-22`).

**What the code actually does.** `apps/sync/scripts/reliability_harness.mjs:27-55` assembles serial commands for those groups; `executeProfile` stops on the first failed step and writes a manifest (`:172-219`). This is orchestration/evidence packaging; proof strength comes from the invoked gates/tests. Its `spawnSync` call has no timeout (`:172-184`), so a hung child can hang the harness. The documentation points to wrappers that provision isolated Postgres/topology resources.

**Current run status / constraint.** The no-argument usage probe works only far enough to print usage (section 4); no profile ran. The default Postgres helper creates a database named `chalk_gate` and provisions a generic gate container/native directory (`scripts/gates/with-postgres.sh:32-35,139-159,186-195`), which does not satisfy this lane’s required unique `lane-a-20260927` resource naming. The topology wrapper similarly provisions its own DB/process topology. I did not invoke either wrapper or create a DB/container. The harness supports supplied test DB URLs (`apps/sync/scripts/with-reliability-postgres:12-19`), but no unique isolated DB was provisioned for this audit.

**What it proves / stale or broken / recommendation.** Its architecture is still relevant and source wiring exists, but this probe does not establish that any profile currently passes. Current code only proves the runner builds the intended plan and records command status; a green profile would prove only the coverage implemented by those scripts/tests. Manifest is useful; per-step timeout/cancellation and a safe, lane-unique resource provisioning mode would improve robustness. **Keep, but fix** timeout behavior and ensure actual CI profile evidence remains fresh before claiming current reliability.

### 3.6 SDK media diagnostics phases (`local_track_state`, `sync_commit`, `sfu_publication`)

**Claim / implementation.** The phases are emitted from `media-controller.ts:216-261`. `local_track_state` is recorded after capture/preparation on enable, or immediately on disable. This is a valid local-track milestone.

`sync_commit` is recorded after awaiting `ports.sync.setMicrophoneEnabled/setCameraEnabled` (`:252-254`), but the V1 live-target Promise includes both the server result and `ports.media.setLocalPublicationTarget` success (`v1-live-target-coordinator.ts:103-135,164-219`). Consequently this phase does **not** isolate a Sync commit/response: on enable it includes browser→API→Cloudflare signaling, SDP negotiation and any connection wait; on disable it includes the server bridge close and local sender removal.

`sfu_publication` is emitted immediately after that same awaited Sync-port Promise and an active-port check (`media-controller.ts:255-259`). It is **not emitted immediately after the Sync commit**: it follows local media-port success. For enable that means the SFU signaling response/publication ID and SDP work succeeded (and possibly connection wait); it does not prove RTP reached another Participant or that their media rendered/decoded. For disable, it follows provider close plus local `replaceTrack(null)`. Since `sync_commit` and `sfu_publication` are adjacent taps after the same promise, they have nearly no independent timing value and the names imply a false decomposition.

**Recommendation.** **Keep the operation timeline but fix the semantics:** separate `sync_result` (immediately on live-target server response) from `local_sfu_signaling_complete`, `local_track_state`, and a distinct remote-observed/rendered milestone. Record request start/end and per-hop IDs so p95 can be attributed.
