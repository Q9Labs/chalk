# 2026-W30 (2026-07-20 – 2026-07-26)

Condensed from 15 session logs. Originals removed on
`chore/docs-scratch-cleanup`; full text remains in git history.

**Chalk went live.** `https://chalkmeet.com/room/` served a real meeting on
2026-07-22, and the rest of the week was spent debugging real WebRTC against a
real provider — where nearly every remaining bug turned out to be a Cloudflare
lifecycle contract Chalk had assumed rather than read.

## The launch audit that started it

A consumer-launch audit of the install-to-joined-meeting path returned a blunt
verdict:

- All three advertised `@q9labsai` SDK packages returned npm **`E404`**. The only
  successful workflow run packed artifacts without publishing; two publish
  attempts failed with `E404` and `EOTP`.
- The React package is intentionally presentational, and the React Native
  provider constructs an **inert placeholder `ChalkSession`** — native join,
  create, media, moderation, chat, recording, whiteboard, and diagnostics cannot
  drive a meeting.
- API-key models and scopes existed with **no public HTTP verification and no key
  lifecycle routes**. The localhost proof embedded a local bearer and constructed
  a development Sync token in the browser.

Package health was fine (`publint`/`attw` clean, 153 + 6 + 146 tests passing) —
which was exactly the point: healthy package shape, no functional consumer proof.
Two codegen gaps in the supplied inventory turned out to be **stale**.

Scope was then fixed to TypeScript and React web, treating client/core/Sync as
one vertical system, deferring recording, and keeping npm publishing off the
critical path. The launch board explicitly required composing the existing Sync
v3 client rather than reimplementing it.

## SDK web launch P0

Built in three independent lanes — API-key domain, participant-access
credentials, TypeScript Cloudflare SFU hardening — with shared router,
middleware, and generated-contract integration reserved for the primary agent.

Landed: API-key persistence/HTTP/middleware with transactional security audit
records, participant access issuance/refresh, **participant-media-only SFU
routing** with a dedicated bearer scheme, Cloudflare close-tracks, authoritative
publication removal, current/previous media verification keys, a framework-free
`ChalkSession`, and React bindings.

**Access refresh binding, decided deliberately:** ordinary refresh must prove and
reuse the current signed media credential's exact connection; explicit SFU
recovery creates a fresh provider connection. This avoids trusting a
caller-supplied connection ID without adding a persistence table.

**Publication references were the recurring theme.** The API stored versioned
references but never returned them, forcing the SDK to invent a legacy reference.
Add-tracks now returns the exact recorded `chalk_pub_v1` reference on each local
response track; close preflight requires version, connection, MID, and
generation, and rejects stale replacements before any provider close. Legacy
two-field references remain parseable but **cannot authorize a destructive bridge
close** without their missing authority fields.

**Review found real security and correctness gaps.** First round: tenant API keys
could reach global routes; versioned remote publication references weren't
decoded; close requests didn't echo the authoritative reference; replacement
access could retry after a lost response.

Second round found **seven browser-runtime races**: queued recovery loss, unsafe
rejoin from an uncleared failed runtime, stale access-refresh completion,
unbounded awaited recovery attempts, an unstopped closed transceiver, concurrent
screen-capture ownership, and concurrent camera/microphone acquisition. All fixed
with deterministic regressions — plus a late `getUserMedia` completion leak found
during integration, where a stale stream had to be stopped before rejecting it.

**Packed-artifact consumer E2E.** A clean external consumer installs real
generated tarballs via `pnpm add` and runs a two-context Chromium matrix (media,
refresh, recovery, denied-access, Leave leak). The consumer is pinned to pnpm
10.26.2 so a temp-directory install can't inherit a different machine-global
version. Firefox and WebKit remain CI-gated — local Playwright installs
downloaded but produced incomplete bundles. **The fixture does not claim live
Cloudflare traffic.**

## The durable-Leave bridge

The real observability journey exposed a deeper blocker: production Sync had **no
provider bridge configured**, the API private handler was **unmounted**, and no
real provider executor existed — leaving participants stuck in `leaving`.

Closed without a no-op provider: a separate TLS 1.3 mutual-TLS listener with
exact SPIFFE Sync peer verification, authenticated readiness, trace/journey
middleware, bounded outcome telemetry, and coordinated two-server shutdown — all
composed in the API runtime **without exposing a public route**. Plus a real
Cloudflare SFU executor for publication revocation, participant removal, and
session end that reads authoritative publication observations, closes exact
connection/MID pairs, preserves newer participant generations, reconciles
ambiguous results idempotently, treats already-absent provider sessions as
satisfied, and terminally reports unsupported recording/grant effects.

The local launch observability proof then passed end to end: mutual-TLS
acceptance and unauthenticated rejection, participant Leave and Session End
provider receipts, cross-service traces, **eight exactly-once webhooks**, and
Tempo/Prometheus/Loki/Grafana assertions.

## Restoring the meeting UI

The frontend regression was traced to commit `009f0583`: the React SDK kept its
polished visual primitives but **lost the connected full-room components** during
the runtime removal. The historical lobby and meeting shell were adapted to the
current `ChalkSessionStore` contract, keeping the web app a thin SDK consumer.

Two blockers surfaced on the way to a real browser join:

1. The local demo admitted the first member as a **participant instead of host**.
2. Cloudflare's successful track response **omits `location`**, despite Chalk
   attaching authoritative publication IDs. Fixed by projecting `location: local`
   at the API boundary.

Review then found missing remote-audio rendering, camera-coupled screen-share
visibility, a non-durable local host leave policy, and an application-relative
SDK logo. A re-review caught that `continue` **is not an accepted host-exit
policy** — restored `require_transfer` and moved durable demo-host cleanup to the
server-only backend.

## Production infrastructure — first contact

A dedicated `chalk-meeting-broker` route Worker owns the `/local-chalk` contract
in production (Vite keeps routing localhost to the Node BFF), backed by a
SQLite-storage `MeetingSession` Durable Object with exact origin/method/content
validation, secure host cookies, rate-limit bindings, and bounded alarm cleanup.
A two-Worker local Wrangler proof against a service-bound fake API verified
**zero upstream work at browser-session creation**, then host session/admission,
access refresh, guest admission, guest deletion, host session end, SQLite state
deletion, and automatic alarm end across eight authenticated upstream calls.

An `apps/api/cmd/bootstrap-meeting` operator command was added because
**production had no supported first-tenant bootstrap identity** — local system
tokens are rejected outside local, and tenant creation doesn't create an owner
membership. One serializable transaction with an advisory lock produces a tenant,
owner membership, `sessions:write` broker key, and active `cf_sfu` room, with
one-time mode-`0600` JSON output and compatible-resource reuse. Review found four
boundary defects: output failure could strand a committed one-time key, non-local
database TLS wasn't enforced, an omitted environment implicitly bypassed
confirmation, and custom identity flags weren't normalized.

**Deployment surfaced five distinct infrastructure faults, in order:**

1. Unsupported Quadlet keys and Redis command truncation in the target Podman
   release — no service started at all.
2. An unsupported rootless systemd hardening directive in the watchdog.
3. **PlanetScale connection exhaustion restart loop** — the 10-connection API
   pool plus 8-connection Sync pool exceeded the app slots on a 25-connection
   cluster, and readiness-driven container kills left stale sessions behind.
   Reduced to 4 and 2, removed readiness-driven kills so transient dependency
   failures stay recoverable, then recycled the rootless network helper that was
   retaining stale database sockets.
4. Podman reported the publicly ready API container **unhealthy** because the
   scratch image has no shell and the Quadlet health command rendered as
   `CMD-SHELL`. Converted to Podman's command-and-arguments array form.
5. A deterministic **Sync readiness flap** during durable terminal cleanup: the
   Sync consumer blocked its own health mailbox during provider work, and its
   four-second bridge timeout was **shorter than Cloudflare Realtime's allowed
   five-second connection wait**, so an expired SFU session returned HTTP 410
   after that wait. Fixed with a single monitored poll worker with bounded
   in-flight health, raised budgets, and classifying already-gone provider
   sessions as idempotent completion.

**Live production proof (2026-07-22 19:41 PKT):** the restored React SDK lobby
joined with host camera and microphone, host state survived a full refresh, an
independent guest cookie session received Sync and media access and appeared in
the live participant UI, guest cleanup removed it, and host Leave ended the
meeting and returned to prejoin. A second independent browser surface was
unavailable, so **guest-side WebRTC rendering was not observed** — recorded as
unchecked rather than assumed.

Final audit: five units active, API/Sync/Redis healthy, database pool steady at
six sockets, all pending end-session operations applied, and **160 public probes
over 217 seconds with zero failures**. One pre-fix test receipt remains
historically failed after exhausting 100 retries before the correction.

## The Cloudflare lifecycle lessons

Everything after launch was media debugging, and the same root cause kept
recurring: **Cloudflare's session contract has timing requirements Chalk wasn't
honouring.**

### Media toggles fail (`dependency_unavailable`)

Traced to boot composition — the configured provider-bridge media plane was
passed to the durable consumer but **not installed where live room sessions
resolve media dependencies**. Two follow-on blockers behind it: live requests
omitted the participant generation, and the API treated browser-owned publication
grants as unsupported.

Then live output exposed a second failure: **API CORS preflight omitted `PUT`**,
so the client could not close active SFU tracks after disabling a publication.

Then a third: Cloudflare rejected an add-track after **5.335 seconds** while
production used a ten-second timeout, and a host-side probe ruled out DNS, TLS,
credentials, and connectivity. The five-second signature is documented behavior —
**follow-up track operations wait up to five seconds for a connected
PeerConnection**. The SDK had been marking media live immediately after applying
the first SDP answer, while peer and ICE state could still be `new`, and it sent
a false-mode close without the required SDP offer. Fixed with a bounded connection
barrier, explicit force-close signaling, and fresh opaque track names per
publication attempt.

The API's add-track adapter was also **discarding Cloudflare error fields during
JSON decoding** — it now validates top-level and per-track failures and exact
local result identity while keeping provider descriptions and media identifiers
out of returned errors.

### Screen share resets the room

Production report: starting a screen share immediately showed "connection reset,"
all participants entered reconnecting, and the initiator reported an exhausted
media recovery budget. That message comes from the SDK after recovery fails in a
bounded ten-second window — **it does not identify the initiating fault**, and
the room-level wording masked that Sync stayed connected.

Correlation found five `POST /media/sfu/tracks` 503s for the initiator, then
~five-second add/close failures from another participant, with API and Sync
containers healthy and no Sync room reset.

The SDK regression: **incremental screen publication reused the initial-connection
wait after the successful offer/answer exchange**, and any local add or remote
pull error promoted the entire media client to failed — so each participant
independently entered full media recovery.

Contained: incremental publication no longer re-runs the initial wait on an
already-live peer, a failed local offer rolls back, desired screen state clears
after a failed attempt, remote discovery is asynchronous and operation-scoped,
and duplicate delivery of the same immutable failed snapshot cannot queue
recovery twice.

The Go adapter gained **privacy-safe diagnostics** — failures classified by
bounded operation, failure stage, HTTP status class, and normalized provider code,
with the public error mapping still generic and no response descriptions, SDP,
secrets, or media identifiers retained.

### Controls roll back (`setMicrophoneEnabled was not confirmed`)

No browser SFU request followed the failed enable, proving rejection happened
during **Sync authorization, not local publication**. The client retry budget
exhausted after three short server responses while the Sync provider bridge
allows multi-second durable work. Extended only the live-target server-
confirmation path to a bounded fifteen-second exponential retry with a hard
attempt cap. Also removed the redundant client-side Cloudflare close after Sync
has already confirmed the revoke.

### Camera re-enable fails after repeated toggling

Correlated with a real add-track and an upstream **HTTP 410**. Reversing the
toggle order showed camera and microphone republishes both work until
**cumulative stopped SDP media sections exhaust the provider budget** — the
failure was source-order independent. The Cloudflare media client now retains and
reuses each source's transceiver and MID across temporary disables (including a
newly prepared screen capture), and failed republishes detach the reused sender
for a safe retry instead of consuming another media section.

### Safari joins with zero media

An empty local stream bypassed SDP negotiation but still moved the media snapshot
to `live`, so the first later screen publication used the **original dormant
Cloudflare connection**. Rather than publish fake audio/video, the fix is a
just-in-time participant-access connection replacement: the media client replaces
only an _unnegotiated_ connection before its first later local publication.
Extended through the first remote-track pull, where a physical PeerConnection
epoch invalidates events from the closed connection **without changing the
logical recovery generation**, so a concurrent first remote pull and first screen
publication serialize through one replacement and both use the fresh connection.

## Smaller items

- **API meeting profile:** non-local config hard-required Composio and
  `cmd/main.go` hard-required the transcription worker bundle. Added strict
  capability flags, fail-closed provider validation, disabled-service
  composition, and bounded readiness — verified by starting an artifact with both
  capabilities disabled and observing `GET /readyz` return Postgres `ok` with
  integrations and transcription `disabled`.
- **Deadline scheduler FK failure:** the local database held overdue pre-sync
  sessions with no `sync_session_control`; the global claim query selected them
  and then tried to create an operation that requires sync control.
  `ClaimDueSessionDeadlines` now restricts to sessions joined to
  `sync_session_control`.
- `golang.org/x/text` upgraded v0.38.0 → v0.39.0 (GO-2026-5970); `govulncheck`
  clean.
- The SDK package gained a **`workerd` export condition** so Workerd resolves the
  real server client while browser and React Native conditions keep resolving the
  server-only guard.
- Repeated Vitest timeout friction under concurrent workspace coverage — an HTTP
  trust-boundary test and a 200-iteration Sync v3 stress test each passed alone
  but exceeded the five-second default in the full run. Given explicit scoped
  budgets rather than reduced assertions.
- API performance stayed healthy throughout: 11.3k–13.7k req/s across stress
  phases.
