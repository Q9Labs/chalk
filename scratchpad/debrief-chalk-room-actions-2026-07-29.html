The room can now talk, react, draw, and ask

Implementation debrief · 29 Jul 2026

The browser room now carries durable chat, short-lived reactions, host controls, consent-based microphone and camera requests, and a shared drawing board. The release is not done: the default mobile runtime cannot yet create the canonical room store, and the drawing board has not run end to end against real object storage.

Background

The turnkey room could join, leave, publish media, share a screen, raise a hand, and show the roster. Lower layers held some host controls, but the product did not expose them. Chat, reactions, and a shared board stopped short of a complete public path.

Before

One canonical room store owns room actions and projects immutable state to web and mobile adapters. Chat and reactions share the existing Sync v3 connection. Only the board uses whiteboard-v1.

Verdict — needs attention. The browser implementation and the server paths are substantial and well tested. Do not call the whole room experience complete until a default mobile room can use these actions without an injected store and a real browser completes board file upload, finalize, download, and cleanup against R2.

What landed

  • Negotiated chat and reactions on Sync v3, with old-client fallback.
  • Room-wide chat in Postgres; reactions stay short-lived.
  • A separate whiteboard-v1 connection with an Excalidraw-compatible reducer.
  • Browser chat, reactions, moderation, ask-to-unmute, ask-to-start-camera, and board controls.
  • Participant-authenticated staged board file transfer and seven-day cleanup.

Deliberate fences

  • No recording controls.
  • No native mobile board.
  • Media requests never turn on a device by force; the target accepts or declines.
  • A slow board cannot consume the room-control queue.
  • Unsupported mobile actions stay disabled instead of calling old no-op methods.

Findings and next moves

Major · Correctness · Default mobile room. Mobile hooks can call the canonical store only when the app injects one. The default provider has a bearer token and a legacy no-op room shell, but the real store needs renewable participant access plus a real media client. Next: define the native bootstrap contract, return renewable participant access, and add the supported native media adapter before claiming mobile parity.
Major · Release proof · Board files. Unit and service tests prove the state machine, but no real browser has uploaded and finalized an image in R2, loaded it as another participant, then observed retention cleanup. Next: run that exact two-participant scenario in a non-production environment with the real provider.
Major · Review coverage. The required exact-commit review ran once and timed out with no verdict. A clean automated gate cannot replace defect review for a cross-stack change. Next: ask for a fresh review pass when review capacity is available; the current handoff must remain needs attention.
Minor · Repository security gate. Five fixable dependency advisories keep the scoped commit gate red even though they predate this change. Next: handle them in a dependency-only change with its own regression run.
