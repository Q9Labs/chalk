# Observability

API request logs, API metrics and Sync event spans export to Axiom. The private table `observability_journey_events` is the durable correlation record for webhook and recording lifecycles. Code defines the event names, fields and metrics; search it (`apps/api/internal/observability`, `apps/sync`) instead of trusting a list here. This page keeps the rules and the reading judgment.

## Correlation

- Every operation is a trace and the request ID is the trace ID. Carry `traceparent` across every hop, including workers, the recorder and the dispatcher.
- A session is one run of a Chalk app on one device. The SDK sends it as W3C `baggage: session.id=<uuid>` on every API request and in the Sync `hello` frame. The API and Sync copy a valid lowercase UUID onto spans and logs and ignore anything else. It is never an Episode, a Cloudflare session or a dashboard `sessionId`. It is not written to the ledger, to Sync frames sent back, or to durable rows.
- Every API response names its request in the `x-chalk-journey-id` header, which CORS exposes. The same ID is `journey_id` on the request log line, on logs and spans started under the request, and on the ledger rows it writes. The client never sends one: the ledger keys one lifecycle by its journey ID, so an ID shared by a session would merge unrelated joins and recordings. Follow a device by `session.id` and one failure by its journey ID. The SDK keeps the latest failed response's journey ID (`lastFailedRequest`), and web problem reports print it as `Last failed request: <journey id> (HTTP <status>)`.
- The `http.request` log line carries `route` (the matched pattern, `unmatched` when none), `status`, `tenant_id` when the route has a valid `{tenant_id}`, and `error_code`, the public API code of a failed response, so a 403 or 409 names the rule that refused it. When a provider's refusal sits behind another public status, the line and the `http.failure` line add `upstream_status` and `upstream_code`; a code that is not a short lowercase token is logged as `unsafe`. The server span and the `journey.phase.http` span carry `http.route` and `tenant.id`: group latency by `http.route`, never by path.
- The API injects `traceparent`, never `baggage`, into its calls to the Chalk SFU and into webhook deliveries, so the session ID stays inside Chalk.
- Deploy the API and Sync before the SDK, and keep `Baggage` in the API's CORS allow list. An older Sync rejects a `hello` that carries baggage, and the SDK then retries once without it.
- Dataset names, tokens and monitor IDs are private deployment inputs. This repo is public, so keep them out.

## Follow an incident

Start with the Episode ID, plus the participant ID, the server error code and the trace or request ID from a failed join. In the API log or Sync trace dataset, run `| search "<episode-id>"` and then narrow by Tenant, Space, participant or trace ID. To see everything one device did, including requests before the join and across several joins, filter `['session.id'] == "<session-id>"` in both datasets. A user can quote the session ID from Call details or a problem report.

A missing failure report does not prove success. A worker can lose its lease or its API connection before it reports. Join recording events by operational job and worker attempt, not by Tenant or Episode.

## Rules for new telemetry

A terminal failure, rejection or timeout must say why, in a bounded and redacted form ([coding standards](../CODING_STANDARDS.md)).

- Tags and metric attributes use a fixed, small set of values. A metric never carries an Episode, Tenant or Participant ID. Put the ID in a log line and search the log.
- A caller is named by its matched `route` pattern, never by an ID. `chalk.api.participant_media.authentication` carries `outcome`, `reason` and `route`, and the log line `participant_media.authentication` adds the `trace_id` that leads to the `http.request` line with the path.
- Counters in the production metrics dataset are cumulative: each export repeats the running total. Read them with `prom::rate` or by the difference of the first and last point of a window. Summing the exported points counts every event once per export, so a counter stuck at 29 reads as 1,740 an hour.
- Allowlist error text. Provider descriptions, raw transport errors, SDP, URLs, paths and anything media-derived can echo hosts, addresses or content. Export a code class, a fixed phrase or a hash (`provider_message_fingerprint`, `participant_id_hash`) instead.
- Tokens, grants, authorization headers, tool arguments, transcript text and audio never enter a log, span or metric.
- Bound state kept for diagnostics (entries, bytes, age), and make a full or failed diagnostic degrade to silence. Diagnostics must never fail the user's operation.
- Count a decision once and name the outcome (`moved`, `refused_no_room`), so a rate shows what is wrong.
- Sample success, keep failures.

## Journey ledger and proof

Add a ledger event when a durable lifecycle boundary changes: the Episode, a participant, a publication, a recording, a webhook delivery. Do it in the same transaction as the change, link it to the parent event, and carry trace and span IDs. The webhook events are listed in `contract/webhooks/v1/journey-events.json`. MCP adds no parallel ledger. A capture claim writes `recording.claimed` to the Recording's start journey in the claim transaction, with `claim_lag_ms` and `placement`, so a slow start reads off the Episode's own timeline. A Recording that ends in `terminal_failure` writes `recording.failed` (phase `recording_failure`, with `recording_id` and `failure_code`) to the same journey in the same transaction, from the pipeline trigger, so every path that fails a Recording leaves one. Proof: `apps/api/internal/adapters/postgres/recording_failed_state_integration_test.go` drives an empty capture and checks the row, the Recording state and the ledger event; the success path in the same file checks that no failure state or event appears.

Every Episode end records why it ended: `episodes.end_reason` is one of `maximum_duration`, `ended_by_participant`, `tenant_recovery` (the host or dashboard ended it for everyone) or `linger_expired` (everyone left and the linger window ran out). Sync emits it on the `sync.episode.ended` span with `episode_id` and `end_reason`, linked to the trace of the operation that ended the call, so "why did this call end" is one search for the Episode ID. The reason is a bounded enum, so it is also safe as a metric attribute, unlike the ID.

Do not add a ledger event for transient delivery that the client observes, such as a congestion pause, a retry, an ICE detail or a diagnostic sample. Their evidence is logs, metrics and call stats. Telemetry from the SFU cannot replace durable Postgres lifecycle evidence.

How a Participant's media session ended on the Chalk SFU is not a ledger event. The node reports it once, when the API ends the Episode, so it is not part of a transaction that changes the Participant, and it is no webhook. It has its own table, `participant_media_sessions`, with one row per session (see [Follow one Participant through the Chalk SFU](#follow-one-participant-through-the-chalk-sfu)). Its proofs are `TestSessionOutcomesAreSavedOncePerSession` (rows, once each, no row for a Participant the Episode does not hold), `TestEndEpisodeSavesHowTheNodesSessionsEnded` (the end saves the outcomes and retries when it cannot), and the SFU's `TestEndEpisodeReportsEachParticipantSessionOutcome`.

When a lifecycle boundary changes, update the ledger and the executable proof in the same change. The proof is a test that drives the real journey and checks the ledger rows, the trace correlation and the redaction. A success path alone is not enough: check that a rejected or failed report emits no success evidence.

## Diagnose one call

`pnpm diagnose:call <episode-id>` reads the database, the API, client and SFU log dataset, and the Sync trace dataset for one Episode, and joins every row by id (Episode, connection, journey, trace). It prints a verdict, a summary, a timeline for each Participant and a list of missing data. Each timeline step names its stage, the side that owns it (client, API, Sync, SFU or recorder, or unknown when the rows do not say) and the ids of the rows that prove it. It needs `AXIOM_TOKEN`, `AXIOM_ORG_ID`, `CHALK_LOG_DATASET` and a read-only `CHALK_DATABASE_URL`. `CHALK_TRACE_DATASET` defaults to `chalk-prod-traces`; a token that cannot read it makes Sync a missing source that blocks the verdict.

What the SFU telemetry adds to the report:

- **Outcomes.** The node's `outcome` and `outage_ms` decide the verdict, not only the `cause`. `never_connected`, `failed` and `dropped` are failures on that side. A session that went down and came back with `outage_ms` is a recovered drop with its length. It passes by itself, and it fails the Wi-Fi criterion (a 10 s drop recovers without anyone else rejoining) only when another Participant started a second session while it was down.
- **Media quality.** From `sfu.media.ingress`, `sfu.media.egress` and `sfu.media.transport`, each publisher's uplink and each subscriber's downlink get loss, jitter, round trip, bitrate and layers, and a starved viewer is placed on one leg: the publisher's uplink, the node (its pacer dropped video, `dropped` on the transport row) or the subscriber's downlink (loss or round trip in the subscriber's own reports with nothing dropped at the node). With no transport row the side stays unknown. Counters are read as the node writes them: ingress `lost` can fall after a late repair, so the packets that did not arrive first time are the growth of `lost` plus the growth of `repaired`; a fall in `packets` is a recreated track and that interval is skipped; egress totals are not read at all, only the loss share, round trip and jitter gauges. Rows further apart than 35 s are no interval.
- **Mute and unmute.** Others should see a mute within 1.25 s and hear an unmute within 2.25 s, both at p95. The report gives the node's legs per unmute (applied to first voiced packet, and first voiced packet to first forwarded packet for each subscriber) and the call's p95 against the budget. The click and receiver playout legs come from the client lane, and are listed as missing data until its rows exist.
- **Durable outcome.** `participant_media_sessions` (one row per session) and `media_plane_changes` are read from the database, which keeps them after Axiom's 30 days. An Episode older than that is read from the database alone and the report says what is gone. Axiom's closing line and the durable row for one connection are one finding. The plane the Episode was bound to and any plane setting change made during it are in the summary.
- **Coverage.** A durable outcome with no `sfu.session.closed` line, and a connected session with no `sfu.media.*` rows, are missing data that point at the `chalk.sfu.telemetry.dropped` counter and the `logs_export` gauge, so a lost export is not read as a good call.

A source it cannot read is a gap, never a silent omission. When no rule finds a failure and a source is missing, the verdict says "Not enough evidence" and names the source. `--strict` exits 3 when it finds a bad call and 2 when it found none but evidence is missing. The thresholds are in `infrastructure/observability/production-alerts/call-verdict.json`. A new event needs a rule in `scripts/diagnose-call/rules.mjs` and, to read well, a line in `scripts/diagnose-call/timeline.mjs`. CI runs the checker's tests when those files, or the code that writes the rows it reads, change.

## Client telemetry

Every SDK client reports what it saw of its own calls to one route, `POST /v1/tenants/{tenant_id}/telemetry`, and the API logs one Axiom row per event with `event = "sdk.telemetry"`. The body is `{ version: 1, client_session_id, events: [...] }`, at most 100 events and 64 KiB. A client session is one run of the SDK on a device, and its events carry a `seq` that counts up from 0 and `elapsed_ms` since the session began, so a gap in `seq` is loss that the server can see. Started events (a join started, the device went offline, the page was hidden) are sent at once, so the server learns of an abandoned join or a lost connection even when the client never sends its end.

The credential is the participant's media credential, the earliest one the join holds. The API accepts it until it expires, including after the participant leaves, because it only stamps rows and the byte budget bounds it, so no new token type or scope exists. The tenant, Space, Episode, participant, provider and `provider_session_id` on a row come from the credential, never from the body. The body carries only closed labels and bounded numbers: an event with an unknown field, a label outside its list, a number outside its range or a field its type does not allow is rejected alone, logged as `sdk.telemetry.rejected` with a fixed `reason`, the `type` and the `seq`, and counted in the response (`{ accepted, rejected }`). The rest of the batch is kept. Tokens, SDP, device labels, addresses, free text and audio content cannot pass.

Each participant has one budget of 4 MiB of request bytes, which refills over 135 minutes. It holds a 135-minute, six-person call with room to spare, and sibling paths share it: a batch costs its bytes whether its events are valid or not. A refused batch gets 429 with `Retry-After` and is logged as `rate_limit.exhausted` with the policy `v1.telemetry.intake`.

To compare providers after a cutover step, or when a failure points at one provider:

```apl
['<api-log-dataset>']
| where ['attributes.event'] == "sdk.telemetry" and ['attributes.type'] == "call_stats" and isnull(['attributes.gap'])
| extend provider = iff(tostring(['attributes.provider']) in ("cloudflare_sfu", "chalk_sfu"), tostring(['attributes.provider']), "unknown")
| summarize
    samples = count(),
    rtt_p50 = percentile(todouble(['attributes.rtt_ms']), 50),
    rtt_p95 = percentile(todouble(['attributes.rtt_ms']), 95),
    recv_loss_p95 = percentile(todouble(['attributes.recv_loss_pct']), 95),
    freeze_rate = sumif(todouble(['attributes.freeze_count']), isnotnull(['attributes.freeze_count'])) / count()
  by provider
```

Add `['attributes.connection_type']` to separate relayed calls from direct ones, or `bin(_time, 1h)` for a trend. Nothing pages on this query.

**Completeness of one client session.** Group the rows by `client_session_id`. The first `seq` should be 0 (a later first `seq` lost the start), the `seq` values should have no gap (each gap is loss: a refused batch, a `telemetry_dropped` count, or a client that died before it sent), and the last event of a clean session is `call_ended`. A session with `join` `started` and no later join event is an abandoned join. After a leave, the client may still send until its credential expires, so wait five minutes before you call a session cut short.

A failed chat file upload is `chat_upload_failed`, with `upload_failure` naming where it broke: `initiate_failed` or `finalize_failed` (an API error), `storage_rejected` (storage answered with `http_status`), or `storage_unreachable` (the browser got no HTTP answer from storage: a network failure or a CORS block). `storage_unreachable` from a browser that otherwise works means the bucket CORS rule is wrong.

SDKs from before client telemetry (mobile 3.0.6 and older embedders) still post to `/connection-reports` and `/call-stats`. The API translates their reports into the same rows, numbers their events in the order listed, and marks each row `legacy_route` and `trigger`. Those SDKs replay earlier events in each report, so a row may repeat; the alerts and `pnpm diagnose:call` count a row from the old routes only for the failure its `trigger` names. Both routes and their translators are deleted when those SDKs are gone.

## Follow one Participant through the Chalk SFU

The Chalk SFU ships a fixed set of diagnosis events over OTLP to the dataset the API's logs go to (`service.name=chalk-sfu`), so most bad calls are explained without SSH: why a session ended, whether it ever connected, and how loss, jitter, round trip and bandwidth looked on each side while it lived. The export is a sample of the node's story, not a copy. The journal keeps every line, and a few causes stay there on purpose: error text, SDP, addresses and anything else a peer can influence. The export also loses records without a word if the store is slow or refuses them, unless something counts the loss (see the drop counters below). The store keeps the events for 30 days, so the durable outcome of each session is also saved with the Participant (see below).

Every event carries `event` (also the log body), `tenant_id`, `episode_id`, `participant_id`, `generation`, `connection_id`, `session_kind` and `node_incarnation`. A node-level event, such as a refused Episode or a refused control call, carries `node_incarnation` and the ids it knows; an Episode-level event has no `participant_id` or `generation`. When the API sends `traceparent` and `X-Chalk-Journey-ID` on a control request, the session's later events carry `trace_id` and `journey_id`; a malformed header is ignored. A session closed by a control call, such as the end of the Episode, carries the trace of that call on its `sfu.session.closed` line, so the close joins the API request that caused it. The log resource carries `service.name`, `service.version`, `service.instance.id` (the node incarnation) and `deployment.environment.name`. The dataset's own `session` column, which shows as `session={"id":null}` on these rows, belongs to the API's logs and is never set by the node; join the two sides through `connection_id`, which is the `provider_session_id` of the API's `sdk.call_stats`. Only these events leave the node, by an allowlist in `features/media/sfu/internal/telemetry/export.go`: a record exports when its `event` names a row, with that row's fields only, and each field declares its source (server-assigned, enum, number or restricted id), and a value a Participant or peer chooses, such as an SDP `rid`, is mapped to an enum first, with the raw value left in the journal. Error strings, the standard library's own diagnostics (a TLS error names the peer address) and every other line stay in the node's journal, so an event reports a cause code, never the error text. A new event or field needs a row in that table, and a test fails until it has one.

The events and their fields are the tables in `features/media/sfu/internal/media/events.go`; the notes here add what the values mean. The events are `sfu.session.registered`, `sfu.session.refused` (`code`), `sfu.admission.refused` (`reason`), `sfu.peer.state`, `sfu.ice.state` (with `path` once connected), `sfu.dtls.state`, `sfu.negotiation.failed`, `sfu.control.failed`, `sfu.publication.started`, `.stopped` and `.held`, `sfu.subscription.started`, `.stopped`, `.paused`, `.resumed` (`reason`), `.layer` (`layer`: `high`, `low`, `single` or `other`) and `.congestion`, `sfu.camera.plan`, `sfu.source.lease_opened` and `.lease_lost` (`cause`), `sfu.media.ingress`, `sfu.media.egress`, `sfu.media.transport`, `sfu.unmute.first_voiced`, `sfu.unmute.first_forwarded`, and `sfu.session.closed`. A source lease that only expires logs no event; its subscribers show `reason=source_unauthorized` in `/inspect`.

**How a session ended.** `sfu.session.closed` carries two fields that answer different questions. `cause` is the first thing that closed the session (`removed`, `replaced`, `episode_ended`, `never_connected`, `peer_failed`, `peer_closed`, `negotiation_failed`, `retired`, `node_shutdown`); it never changes after the first. `outcome` is what that meant for the call, and it is the field to read first: `left` (the peer closed a healthy connection), `dropped` (the connection failed, or closed while it was down), `never_connected` (the session never had a media path, whatever closed it, so the Episode ending on a session that never connected reads `cause=episode_ended outcome=never_connected`), `failed` (an offer or answer could not be applied), `interrupted` (the node stopped) and `ended` (the API or the Episode ended it). The line also carries `connected`, `lifetime_ms`, `connect_ms` (once connected), `disconnects`, `outage_ms` (the time spent down, including an outage still open at the close), `last_ice_state` and `last_peer_state`. A `peer_closed` with `outcome=left` is a clean leave and is logged at info level; `dropped`, `failed` and `never_connected` are warnings.

**Outage and recovery.** `sfu.peer.state` with `state=connected` carries `connect_ms` on the first connect, and `outage_ms` when it ends an outage, so a recovery pairs with the `disconnected` that began it by the same `connection_id` and tells the length of the gap.

**Why a negotiation or control call failed.** `sfu.negotiation.failed` names the `step` that failed (`offer_tracks`, `gather_ice`, `read_offer`, `apply_offer`, `answer_offer`, `apply_answer`, `apply_close_offer` or `answer_close_offer`) and a `reason` of `timeout`, `canceled` or `rejected`, never the library's error text. `sfu.control.failed` is written when a control call fails, including the refusals that carry no scope, with the `operation`, the HTTP `status` and the problem `code`, and the call's trace.

**Call quality on the node's side.** Every 10 seconds the node writes, for each connected session, one `sfu.media.ingress` event per published track, one `sfu.media.egress` event per media kind that session receives (`audio`, `video`), and one `sfu.media.transport` event. The counters are cumulative while the track lives, so a rate is the difference between two events, and one lost event costs nothing. Two exceptions: ingress `lost` counts packets still missing, so a late repair lowers it, and an egress total drops when the subscriber closes a track, because the closed track's counts leave the sum. A track whose counters stop moving writes one more event to show the silence begin, then none until it moves; a session that closes writes a last set with `final=true`. The events cost a fixed amount per session and track and take no part in forwarding.

- `sfu.media.ingress` (uplink, publisher to node): `source`, `media_kind`, `mid`, `packets`, `bytes`, `lost` (packets missing at the node and not repaired), `repaired`, `nack_requested`, `keyframe_repairs`, `pli_sent`, `jitter_ms` (RFC 3550 interarrival jitter), `bitrate_bps`, `layers`, `layers_active` and `held` (the track was muted, so a gap is not loss).
- `sfu.media.egress` (downlink, node to subscriber, from the subscriber's own RTCP): `subscriptions`, `paused_subscriptions`, `high_layer` and `low_layer` (subscriptions on each simulcast layer), `pli_received`, `fir_received`, `nack_received`, `lost` (the subscriber's cumulative loss), `loss_share`, `jitter_ms`, `rtt_ms` and `bitrate_bps`.
- `sfu.media.transport` (the session's send side): `estimate_bps` (the bandwidth estimate), `proven_bps`, `queued_bytes`, `probing`, `feedback_age_ms`, `sent_audio`, `sent_video`, `sent_repair`, `sent_probe`, `dropped` and `repairs_cut`.

To tell which side a bad call is on, compare the same minute on both: ingress `lost` and `jitter_ms` rising for a publisher's track mean the publisher's uplink is bad and every subscriber sees it; egress `lost`, `rtt_ms` or a falling `estimate_bps` for one subscriber with clean ingress mean that subscriber's downlink is bad; both clean with a client report of freezes points at the client.

**The node's share of an unmute.** The owner's criteria are that others see a mute within 1.25 s at p95 and hear the unmuted voice within 2.25 s at p95. The node stamps its legs on its own clock, one set of events per unmute of a microphone, and the client lanes stamp theirs; the node never sees the client's clock. Three events tell the node's part, none of them with audio or a level.

- `sfu.publication.held` is written on the publisher's session when the node applies a mute (`held=true`) or an unmute (`held=false`), so the time of the line is when the node applied it. It carries `source`, `media_kind`, `held` and `unmute_seq`, which is the number of unmutes of this publication so far, counted from 1. A mute carries the number of the unmute before it, so mute and unmute pair as `unmute_seq` n and the next n+1.
- `sfu.unmute.first_voiced` is written on the publisher's session when the first voiced packet after an unmute reaches the node. It carries `source`, `unmute_seq` and `since_unmute_ms` (the node's apply time to that packet's arrival). A packet counts as voiced when its RFC 6464 level is at or below 50 dBov, the same line that picks the active speaker. Silence, speech sent into a mute and every later packet write nothing, and a microphone that did not negotiate the audio level extension writes no unmute events at all.
- `sfu.unmute.first_forwarded` is written on the subscriber's session, once per subscription, when that same packet is written to the subscriber's transport. It carries `publisher_id`, `source`, `mid` (the subscriber's MID), `unmute_seq`, `since_unmute_ms` and `since_voiced_ms` (the node's own time between receiving and sending the packet: the forwarding leg). A subscription that is paused, joined after the packet or could not send it writes no event for that unmute, and the missing line is the signal.

The key of an unmute is the publication plus its `unmute_seq`. A publication is `tenant_id`, `episode_id`, `participant_id`, `generation`, `connection_id` and `source`, and a subscriber is the `connection_id` of the session that logs `first_forwarded` with the publisher's `participant_id` in `publisher_id`. The join from a client's own events has two legs. The first is exact: the client's `media_intent` and `media_result` carry `op_id`, and Sync stamps the same value as `operation_id` on `sync.media.intent` (`participant_id`, `source`, `enabled`, `at_ms`) when the socket takes the live-target command, in the socket's own trace. The second leg is by participant and time: the `sync.media.intent` line has the `participant_id` and `source` of the SFU's `sfu.publication.held` line, and the first `held` line of that source after its `at_ms` is the one it caused, so its `unmute_seq` is the number the three SFU events share. It holds across a republish or a recovery, because a new publication generation starts its own count and the time order still picks the line that follows the stamp. A retry resends the same `operation_id` and writes another stamp, so read the earliest stamp of an `operation_id`: it is when Sync first took the command, and a later stamp never matches a later unmute because each unmute has its own `operation_id`. The SFU events do not carry the `op_id`, and the client does not guess an `unmute_seq`. The mute leg on the node is the time of `sfu.publication.held` with `held=true` against the API's request for the same Participant; the audio leg is `first_voiced` and `first_forwarded` against `held=false`.

`sync.media.intent` is the Sync log line for a live-target command (mute, unmute, publish, unpublish, share start and share stop). It is written when the socket takes the command, before Sync applies it, and again for each retry of the same `operation_id`, with `operation_id`, `participant_id`, `source`, `enabled` and `at_ms` (Sync's clock, in milliseconds since the epoch).

**From a problem report to its client events.** A report's diagnostics carry `Client session: <uuid>`, which is the `client_session_id` of the sender's telemetry rows. When the report is accepted, the client sends `problem_reported` at once, so the rows of that session around that event are what the person saw before they wrote. A report sent from the screen after the call has ended carries the same `Client session` line but no event, because the client has already sent its last events and stopped. The report holds no event data itself.

**What the export loses, counted.** The node exports through a bounded queue of 2048 records. When the store is slow, refuses a batch, or a field fails its source check, the node drops the record or field and counts it in `chalk.sfu.telemetry.dropped` with `reason` `queue_full`, `export_failed` or `field_rejected`; failed batches also add to `chalk.sfu.telemetry.export_errors`. `chalk.sfu.telemetry.logs_export` is 1 while the trail is exported and 0 while it stays in the journal only. Without `OTEL_EXPORTER_OTLP_LOGS_HEADERS` the node still starts, writes one warning to the journal that says the export is off, and the gauge reads 0, so the missing token is visible on the metrics the node already ships. Alert on that gauge being 0 on a node that should export. A shutdown flushes the last records for at most 3 seconds, inside the container's 20-second stop limit.

**The durable copy.** The store keeps the events for 30 days. When the API ends an Episode, the node answers with how each Participant session of the Episode ended, and the API saves each in `participant_media_sessions` with the Participant (`connection_id`, `generation`, `cause`, `outcome`, `connected`, `ended_at`, `lifetime_ms`, `connect_ms`, `disconnects`, `outage_ms`). It is one row per session, so a Participant who rejoined has one row for each connection, and saving the same answer twice changes nothing. The node holds the outcomes for a day, so a retry after a lost answer returns the same ones; sessions that ended on a node that restarted before the Episode ended are lost from this table, and the `sfu.session.closed` line is then the only record. A session that ends on an Episode moved to another node has its outcome on the old node's `sfu.session.closed` line only.

```apl
| where ['episode_id'] == "<episode-id>" and ['service.name'] == "chalk-sfu"
| where _time between (datetime(<from>) .. datetime(<to>))
| project _time, event, participant_id, connection_id, state, cause, reason, path, source, layer, trace_id
| sort by _time asc
```

`TestExportedRowsShowWhatHappenedToEachSession` in `features/media/sfu/tests` is the proof of the export: it runs a real node against a local OTLP sink, with one session that never answers and one connected publisher, ends the Episode, and checks the rows the store would receive (`never_connected`, the final media counters, `service.instance.id`, no dropped record). Run it with `-v` to read the rows. Drop the `service.name` filter to see the API's and the SFU's lines together. Deploy installs the export when `~/.config/chalk-sfu/<env>/otlp-log-headers` exists (see the [SFU README](../features/media/sfu/README.md)); without it the node logs to its journal only.

## What an alert means

The rules, thresholds and delivery setup are in [production alerts](../infrastructure/observability/production-alerts/README.md). The Chalk SFU on-call steps are in its [runbook](../infrastructure/observability/production-alerts/sfu-runbook.md). The listener audio check is in [its README](../infrastructure/listener-audio-alert/README.md). The judgment behind them:

- **TURN credentials fail.** The join continues on STUN only, so clients on UDP-blocked networks cannot connect media. One failed mint is a blip, so the monitor pages on three in five minutes. Find the affected class by searching the log for the Episode ID.
- **Chalk SFU recovery refused.** A live Episode on a silent or restarted node moves through one generation-fenced binding change. A sustained `refused_*` outcome means live calls cannot leave a lost node, so check pool capacity first. A single `moved` is still worth a look at the lost node.
- **Retirement debt stuck.** A moved or ended Episode owes a retire to each node it left. The Episode end counts as confirmed once the debt row is durable, not when the node acknowledges. A healthy fleet pays a debt within seconds, so a debt older than 15 minutes means a node has stayed silent through many backoff cycles. Check that node, and restart it if it is up but not answering control calls. A silent node keeps its sessions until it restarts, but media stops within the source lease TTL because the API stops renewing the lease.
- **Sync stays unready.** Sync's own probes already apply hysteresis, so paging on each probe would be noise. The rule needs three unready minute samples in four, so a total outage turns the monitor red about three to four minutes after Sync stops. It ignores a short blip and catches a sustained outage, and it repeats every 30 minutes while it stays red. Missing samples do not prove continued unreadiness, so a lost host is caught by the freshness monitor, which turns red when a rule wrote no row for three minutes and names the rule. The collector also writes `database-unreachable` (the one row that still carries the failure when the database is down) and `runtime-health` (the API and the tunnel, as the host watchdog checks them), and the API `/readyz` body reports `sync` (`connected` or `disconnected`) without changing its status.
- **Listener audio.** An unpulled publication (Cloudflare SFU only) or `audio_receive_stuck` client reports from at least two distinct participants on one Episode page Oncall. The client report is the provider-neutral signal. Point `CHALK_AXIOM_LOG_DATASET` at the production API log dataset only: the query does not filter by environment, so a dataset that also holds nightly logs would page for nightly.
- **Connection-report rules.** They alert on one affected participant per Tenant, Episode and failure. A cleared threshold does not prove the person rejoined or recovered.

Process-local diagnostics, such as the listener publication sampler, reset on an API restart. A pull-acceptance signal proves the provider accepted the pull, not that packets arrived or renegotiation finished.

## Hosted MCP

`/mcp` uses the API's HTTP trace context, and each application call adds a child span named `mcp.<operationID>`. Look for `mcp.protocol.rejected` (schema or protocol failure) and `mcp.origin.rejected` (Origin denial). `mcp.oauth.*` events carry grant, tenant and client IDs only. A rise in `reuse_detected` means a client is racing refreshes or a token leaked.

## Transcription

Transcript failures carry a bounded `provider_*` reason (see `apps/transcription-dispatcher/src/errors.ts`) and never transcript text, provider bodies or audio. A silent source completes with no cues and no cost, so it is not a provider failure.

## Recording maintenance events

The API emits `recording.job_recovered` for each job that committed recovery returns, and `recording.reservation_expired` for each expired reservation. "Recovered" means the job row moved to a retry or a terminal failure, not that media was recovered. The `reason` is the committed row's code, not proof of which recovery predicate matched. The reservation event has no job ID, so join it to jobs by Recording ID. Events appear only after the enclosing transaction commits, and they never carry free text, payloads, leases, worker identity or storage paths.

## Recording failures and capture facts

`recordings.status` is `pending`, `processing`, `completed` or `failed`. A `failed` Recording carries `failure_code` (also in the API `Recording`) and `failed_at`. A trigger on `recording_pipelines` sets both when the pipeline reaches `terminal_failure` and clears them when a retry reopens the pipeline, so `Fail`, lease recovery and reservation expiry all take the same path. The code is the terminal job's `error_code`; with none, an unclaimed reservation reads `capture_reservation_expired` and anything else reads `recording_failed`. The `recording.failed` webhook fires from `Fail`, from lease recovery and from reservation expiry.

Codes an operator sees:

- `capture_empty`: the capture completed with no committed media bundle. A bundle with codec `gap` holds no media, so a gap-only capture is empty too. The API decides this from committed bundles at `CompleteCapture`; the recorder needs no protocol change. The job detail carries `media_bundles` and `gap_bundles`.
- `render_<stage>_failed`: the render stage that failed (`download_capture`, `source_preparation`, `commit` and so on). The API keeps only this shape, and `render_attempt_failed` means no stage claimed the error.
- `capture_stopped_before_completion`, `capture_completion_expired`, `lease_expired`, `recording_source_expired` and the other existing job codes pass through unchanged.

`recording_pipelines` holds what a completed capture saw, so an operator can read it without decrypting a manifest: `capture_media_bundle_count` and `capture_gap_bundle_count` (counted by the API from committed bundles), `capture_track_count` and `capture_packet_count` (reported by the recorder in the completion request as `observed`), and `capture_completeness`. All are null for captures that completed before the columns, and the track and packet counts are also null when the recorder is older than the API or the job was a completion-only recovery. The recorder still logs the same numbers as `recording.capture_finished` (`outcome` of `stopped`, `stopped_without_media` or `failed`, `track_count`, `packet_count`, `stop_cause`).

`capture_completeness` is `complete` when the Episode confirmed the stop, and `partial` when the Episode stopped without confirmation and the capture completed from the bundles committed so far. A partial capture is usable, so the Recording is not failed and its exports and transcripts run, but the tail between the last committed bundle and the real stop may be missing. The `recording.capture.salvaged` ledger event marks the same case.

Transcription is independent of the MP4 export. A failed export fails the Recording (`status` `failed`), but a transcription job that already holds a valid lease still commits its prepared source for a failed Recording, as long as the capture completed, the lease holds, the capture is not deleted and the source window is open.

A Recording that ends in `terminal_failure` through lease recovery publishes the same `recording.failed` webhook as `Fail`. Each terminal transition appears in the journey ledger, but the pipeline records the first webhook enqueue, so a failed Export retry does not enqueue another event even after webhook history expires.

A lease that expired during an attempt writes its `recording_job_attempt_failures` row at recovery, since `Fail` never ran. A job that was never claimed has no attempt to record, so its reason stays on the job row.

A Transcript whose source was never built reads "No audio source was available for this recording, so nothing was transcribed." instead of "No speech was transcribed."

## Recorder telemetry

The capture and render binaries (`chalk-recorder-capture`, `chalk-recorder-render`) export logs, traces and metrics through `observability.StartWorker`, the same way the API does. Settings: `CHALK_RECORDER_OTLP_ENDPOINT` (`https://api.axiom.co` for Axiom), `CHALK_RECORDER_OTLP_INSECURE`, `CHALK_RECORDER_ENVIRONMENT` and `CHALK_RECORDER_VERSION`. The OTLP exporters read the credential from `OTEL_EXPORTER_OTLP_LOGS_HEADERS`, `OTEL_EXPORTER_OTLP_TRACES_HEADERS` and `OTEL_EXPORTER_OTLP_METRICS_HEADERS` (an `Authorization` bearer token and the `X-Axiom-Dataset` header). Put the headers in the unit's secret store, never in a deploy template or env file in Git. With no endpoint, nothing is exported and logs go to stderr, so a deployment enables telemetry by adding these variables to the worker unit of each deployment form (the SFU-adjacent capture unit, the recorder images and the managed-episode render unit). The SFU deploy wires the SFU-adjacent capture unit: with `otlp-headers`, `otlp-log-headers` and `otlp-trace-headers` in the operator directory it sets the endpoint and maps the three Podman secrets (steps in `infrastructure/sfu/README.md`). The on-demand fleet's render worker and the managed-episode units are not wired yet.

Every row carries `tenant_id`, `episode_id`, `recording_id`, `job_id`, `attempt` and `capture_epoch`. The claim response carries the Episode's `journey_id` and `trace_id`, so a recorder attempt runs on the Episode's journey and trace; an API that predates them sends neither, and the attempt then uses the claim request id as its journey. Render-started transcription admission keeps the journey and `traceparent` too.

Recorder events: `recording.capture_connection_created`, `recording.capture_media_stopped` (the SFU answered 409 because media had already stopped), `recording.capture_finished` and `recording.render_stage` (`stage`, `outcome`, `duration_ms`). The API records `recording.capture_attempt_failed` and `recording.render_attempt_failed` from the worker's fenced report; the render worker does not log its own copy. Metrics: `chalk.recorder.jobs.claimed`, `chalk.recorder.jobs.lease_recoveries`, `chalk.recorder.jobs.terminal_failures` (API) and `chalk.recorder.render.stage_duration_seconds` (render worker). Alerts are out of scope here; these events and states are what an alert or the diagnose-call checker reads.

## Recorder fleet conflicts

Expected recorder fleet 409 responses emit `recorder_fleet.operation_failed` at info level with `operation`, `error_code` and `http_status`. The codes distinguish inventory that is not ready, pending bootstrap and closed admission. A pending bootstrap with a validated diagnostic also carries its allowlisted `stage`; invalid or missing diagnostics omit it. These events carry no error text, request fields or node IDs. A conflict records a refusal or retry, not proof that a recording failed.

## Media plane changes and decisions

Two events say where Episodes go and why. Both carry bounded values only, never credentials or free text from a request.

**`media_plane.changed`** is one event for each change to a Space's plane, a Tenant's default plane or the Chalk SFU kill switch. A database trigger writes the durable row (`media_plane_changes`) in the same transaction as the change, so the operator command, the public API and the previous release all leave one, and a change cannot happen without it. The API reads the unannounced rows every 10 seconds, logs each once and stamps `emitted_at`, so the event arrives up to about 10 seconds after the change and may repeat after a crash. Fields: `change_id` (dedupe key), `scope` (`space`, `tenant` or `kill_switch`), `tenant_id` and `space_id` when the scope has them, `old_plane` and `new_plane` (`cf_sfu`, `chalk_sfu` or `inherit`; the kill switch is `cf_sfu` while it holds new Episodes on Cloudflare and `inherit` while the settings decide), `actor`, `reason`, `changed_at` and `change_trace_id`. The `trace_id` of the log line is the relay's, so join a change to the command that made it by `change_trace_id`. A writer that names nobody is recorded as `unattributed`; today that is the previous release, which writes only the legacy columns. An undo is another change with its own reason, and a write that changes no plane leaves no row. If the relay cannot read the table it logs `media_plane.changes_unannounced`; the rows stay and go out when it recovers.

**`media_plane.selected`** is one event for each Episode that gets a binding, after its transaction commits, with `episode_id`, `tenant_id`, `space_id`, `provider`, `selected_by`, `configuration_source`, `placement_reason` and `node`. The same `selected_by` is stored in the Episode's binding (`episodes.config_snapshot`, `media_plane_binding.selected_by`), so a checker can read it from the row and need not wait for the event. The event is a log line, so a crash between the commit and the line loses the line and never the stored value. Values:

- `kill_switch`: the kill switch held new Episodes on Cloudflare.
- `allowlist`: the Space is not on the Chalk SFU allowlist.
- `client`: the SDK does not declare `chalk_sfu`.
- `space`: the Space's own setting chose the plane.
- `tenant`: the Tenant's approved default chose it.
- `tenant_config`: the Tenant runs its own Cloudflare credentials.
- `default`: `CHALK_DEFAULT_MEDIA_PLANE` chose it.
- `overflow`: the Chalk SFU was chosen but no node had room, so Cloudflare took the Episode.

The field is additive and checked by shape (lowercase letters and underscores, at most 32 characters), not against this list, so a later release can add a value and a rollback still reads every binding. A binding written before this field existed has none, and its event says `unknown`. A live Episode keeps its binding, so a later change never rewrites `selected_by`.
