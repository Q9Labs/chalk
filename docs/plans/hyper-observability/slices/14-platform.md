# Slice 14: Platform: DB, releases, flags, Cloudflare edge

This slice proves that a platform fault (Postgres down, saturated or locked; a release that didn't take or that broke things; a config change nobody recorded; Cloudflare unable to reach the origin or serve a bundle) shows up as a named finding over a time window, so a broken deploy can't look like "0 joins, 0 errors" (plan `docs/plans/hyper-observability.md:178`). SWE-2 builds it. It owns the `db.` `release.` `flags.` `edge.` prefixes, the Postgres health poller, the edge collector, and the release and rollback markers (plan section 9 parallel work: if they haven't landed when this slice starts, this slice adds them at the files named below). It depends on C1 (`fact`, the envelope's `release_sha` and `flags_hash`, which prints as an `fl_` handle and resolves through C1's `obs.flags_snapshot`), C2 (verdict fields, backstops, three-state readings), C3 (watermarks, `evidence_gap`) and C4 (the line grammar in `docs/diagnose.md`). Slices 1, 2, 7, 9, 12 and 13 read its edge rollups, `release.marker`, `release.started` and the boot `obs.flags_snapshot` (whose flags map carries `request_logs`, the request-log mode slice 12 reads) as witnesses but own their own symptoms. Code facts are at b3dc1d3afa. Today there is a pool ping (`apps/api/internal/adapters/postgres/readiness.go:20`), a host collector that writes a `database-unreachable` row every minute over its own connection (`infrastructure/observability/production-alerts/collector_health.go:15`, `infrastructure/observability/production-alerts/collector.go:652`, `infrastructure/observability/production-alerts/chalk-alert-state.timer:6`), and an alert for an API start that no deploy record explains (`infrastructure/host-change-alert/host-change-check.mjs:45`). ## 4. Rule conditions

Missing data never yields healthy. Each rule's `decide` gets three-state readings and returns `pass`, a finding (`broken`, `degraded`, or `expected` with its reason code and no module) or `unknown` with a reason; healthy comes only from the kernel, when every planned check passed on complete evidence. A gap below means the check is unknown: either `decide` returns `unknown` with that reason, or a required reading is incomplete, and a finding the rule returns from the other readings still prints. A gap prints as `gap: <code> all: <reason>`, and the header's `partial(...)` names the prefix of every check that is a gap, plus `open` while the UTC day hasn't ended. A cause or component named below goes in the finding's fact text, and a finding that carries a hypothesis sets `upstream=witnessed`, since the kernel rejects a hypothesis past an unwitnessed hop. Two witnesses that contradict each other are events of one fact, so the kernel compares their claims and prints a `disagree` line; a rule never writes one. A sample is one `db.health_sample` (every 30 s); "consecutive samples" means adjacent `sample_seq` from the same `service.instance.id`, and a missing `sample_seq` between them breaks the run and counts toward the sample gap below. A bucket is one closed 5-minute UTC `edge.http_rollup` bucket; it counts only when an `edge.collector_tick` with `status=ok` exists for that bucket and host, and only then is a zero count real. An Axiom read with `truncated: true` (`scripts/diagnose-call/axiom.mjs:29`) or a field Axiom refuses (`scripts/diagnose-call/axiom.mjs:36`) is a gap for that source, never zero.

## 7. Out of scope and traps

- Don't touch other slices' prefixes (`boot.`, `join.`, `reconnect.`, `page.` and the rest) or files, the foundation contracts, Sync's Postgrex config, or production config: no `wrangler deploy`, no `wrangler secret put`, no GitHub secrets. The lead creates `CHALK_AXIOM_INGEST_TOKEN`, `CHALK_INFRA_DATASET` and the four worker secrets.
- Don't poll through the pool or `/readyz`: a saturated pool would hide its own witness.
- A 200 from Cloudflare, a resolved `fetch`, or a successful ingest call isn't proof the page loaded or the marker landed. The fixture test reads the row back from the dataset.
- A marker that fails to post never fails a deploy, but it isn't silent either: in production the missing marker turns `release` partial through the GitHub comparison.
- The GitHub record and the marker are one witness. An edge 5xx with an origin 5xx and the API's `http.request` 5xx are one request: never add them.
- An empty query, a missing tick, a truncated read or a missing `pg_stat_statements` is `unavailable(reason)` or a gap, never `0` and never healthy. A status code alone never makes `deploy_restart`.
- Never put raw paths, query text, SQL parameters, tokens, authorization headers, zone IDs, dataset names or monitor IDs in a fact, fixture, `infrastructure/uptime-worker/wrangler.toml` or CLI output.
- Don't count the `health` class as Participant traffic. The cron stays `*/5 * * * *` (`infrastructure/uptime-worker/wrangler.toml:6`).
- Don't add redaction and don't remove existing hashes; C1 owns privacy.
- Out of scope: backup and restore readback, Sync Postgrex pool metrics, Sync `application_name` (a Sync blocker shows as `postgres.other_session`), SFU and recorder host health (slices 2 and 10), and status-200 HTML served for a missing chunk.
