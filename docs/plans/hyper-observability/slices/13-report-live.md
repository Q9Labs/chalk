# Slice 13: Report a problem and live introspection

This slice proves two journeys. First, a problem report a Participant sends is stored in Postgres, findable by a `CHK-XXXX` code, tagged with the symptom the person picked, and followed by one diagnostic upload that the checker downloads from R2 and parses. Second, `diagnose live <who>` reaches a running client through one Sync control frame and gets its state back, or names the hop that failed. SWE-2 builds it from this spec. It owns the `report.` and `live.` prefixes. It depends on C1 (`formatHandle`, `diagnosticCode`, the `jr_`, `cs_` and `dg_` handles, `<ObservedSurface>`, registry), C2 (the `report` source, `BLIND_SPOT`), C3 (telemetry token, source watermarks, `evidence_gap`) and C4 (the line grammar in `docs/diagnose.md`). It reads records from slices 7 and 9 and carries upload parts whose content slices 3, 6 and 9 own. Code facts at `b3dc1d3afa`: a report goes to Discord first (`apps/api/internal/problemreports/service.go:94`) and leaves only a ledger event in Postgres (`apps/api/internal/adapters/postgres/problem_reports.go:75`); a ledger failure after Discord still answers Sent (`apps/api/internal/problemreports/service.go:106`). There is no report table, symptom picker, upload or live request, and no report shows a CHK code.

**Journeys:**
1. A Participant opens Report a problem in the call or on the end screen (`sdks/typescript/react/src/components/chalk/Chalk.tsx:222`), optionally picks the closest symptom, writes what went wrong and presses Send report. They see Sent with a CHK code, or an error. Web only: React Native has no Report a problem today, and this slice doesn't add one.
2. Once the report is stored, the client uploads one diagnostic bundle.
3. An operator runs `diagnose live <who>`. Sync delivers one `live_request` frame to each socket of that seat, each client uploads one bundle, and the CLI prints one `upload dg_x readback=...` line per bundle.

The slice starts when the dialog opens and stops at the R2 readback. It does not judge whether the call was healthy (other slices), fill the flight recorder (slices 3, 6, 9), read edge logs (slice 14) or compute `BLIND_SPOT` (C2).

**Decisions made here:**
- **Commit first.** The `problem_reports` row and the existing `problem_report.delivered` ledger event commit in one transaction before the Discord forward, so Sent means stored. A commit failure answers 503 `reports.not_stored` and keeps the existing `journey_*` causes (`apps/api/internal/problemreports/outcomes.go:60` to `:65`). The forward then runs in the same request (8 s HTTP timeout, `apps/api/internal/adapters/discordreports/adapter.go:37`), its outcome is written to the row, and the response is Sent whatever it returns. No retry. `Available()` returns true whenever the repository is configured, so Discord is optional.
- **CHK code.** The code is the reporting client session's diagnostic code from `observability/registry/ids.json`: `diagnosticCode(client_session_id)` in `sdks/typescript/client/src/obs/ids.ts`, four Crockford base32 characters from the first 20 bits of the client session id. The API computes it at commit with the same function and stores it in `chk_code` with a non-unique index `(tenant_id, chk_code)`. It is a scoped lookup, never an authority: about one client session in a million shares it, so `diagnose CHK-7Q2M` scopes it by Tenant and time and prints every match as a `cand` line. The response becomes `{sent: true, report_id, code}`.
- **Row fields.** `problem_reports` holds id, chk_code, tenant_id (not null, FK to `tenants`), Space, Episode, Participant, generation, `client_session_id`, `sdk_version`, `jr_`, picked_symptom, description, diagnostics, created_at, and forward_outcome (`pending`, `ok`, `not_configured`, `http_<status>`, `transport_<category>`). `client_session_id` and `sdk_version` are new request body fields. `client_session_id` is `telemetry.sessionId`, the outbox ID that keys the client's telemetry rows (`sdks/typescript/client/src/telemetry/outbox.ts:59`, `:235`). It is not the baggage `session.id` from `currentSessionId()` (`sdks/typescript/client/src/session/index.ts:23`), which is a different per-tab UUID. The description lives only in this row and in Discord.
- **Symptom picker** (optional radio group above the textarea; codes owned by other slices, checked against the registry at regen: `join.` slice 2, `audio.` slice 3, `video.` slice 4, `share.` slice 5, `board.` slice 6, `access.` slice 7, `end.` slice 8): "I couldn't join" `join.no_media`; "Others can't hear me" `audio.not_heard`; "I can't hear others" `audio.cant_hear`; "Video froze or went black" `video.frozen`; "Screen share won't stop" `share.wont_stop`; "The whiteboard jumped" `board.view_jumped`; "I got disconnected" `access.connection_lost`; "The call ended wrongly" `end.wrong_screen`; "Something else" stores `not_applicable`; no choice stores `unavailable(not_picked)`.
- **Upload envelope.** One gzip JSON object, `diagnostic_bundle` v1, at most 4 MiB, compressed with `CompressionStream("gzip")`. Parts: `state` (named fields only: connection status, last error code, `cs_`, `pt_`, `ep_`, app and SDK version, `flags_hash`), `surface_tree` and `flight_recorder`. Each part is `observed(bytes)` or `unavailable(not_built | capture_failed | over_budget)`. Until the ring and `<ObservedSurface>` exist, those two parts are `unavailable(not_built)`. An unavailable part never fails the upload.
- **Upload flow.** `POST /v1/tenants/{tenant_id}/diagnostic-uploads {trigger: report|live, report_id|live_request_id}` returns `{upload_id, url, headers, expires_at}` with a 120 s presigned PUT from `CreateUploadURL` (`apps/api/internal/objectstorage/service.go:63`). Key: `diagnostics/<tenant>/<episode>/<upload_id>.json.gz`. The client PUTs, then calls `POST .../diagnostic-uploads/{upload_id}/complete {bytes, sha256}`. The API runs `InspectObject` (`apps/api/internal/objectstorage/service.go:37`) and commits `stored` only when the size matches. Auth is the participant media credential until C3's telemetry token lands. One upload per report and per live request. The API answers 409 `diagnostic_uploads.request_expired` for a live request past its expires_at.
- **Live request.** `POST /operator/diagnostics/live-requests {tenant_id, episode_id, participant_id}` (unversioned, like `/healthz`) checks its bearer by SHA-256 against `CHALK_OPERATOR_DIAGNOSE_TOKEN_SHA256`, read in `apps/api/internal/config/operator_diagnose.go (new)` the way `apps/api/internal/config/operator_read.go:11` reads its hash and compared like `apps/api/internal/httpapi/operator_read.go:11`. Unset, the route answers 404. It inserts a row with expires_at = +60 s and snapshots `participant_status`, `left_at` and `episode_status` from `participants` and `episodes` in the same statement. It answers 409 `live.request_pending` when the seat has an unexpired request and 429 `live.rate_limited` past 10 per Episode per hour. The trigger calls `pg_notify('chalk_live_requests', '<tenant>:<episode>:<request>')`, built like `apps/api/db/schema.sql:3597`. Sync listens the way it does for publications (`apps/sync/lib/chalk_sync/fanout/postgres_notifications.ex:53`). The live Episode process sends `{type: "live_request", request_id, expires_at_ms}` to the seat's registered sockets (`apps/sync/lib/chalk_sync/live/episode.ex:67`) that opted in with the query `live_introspection=1` (same pattern as `sdks/typescript/client/src/sync/entry-url.ts:9`, `apps/sync/lib/chalk_sync/transport/router.ex:97`, `apps/sync/lib/chalk_sync/protocol.ex:46`), and writes `delivery` (`delivered(n)` or `target_unavailable(no_socket | not_negotiated)`) to the row. The client answers `{type: "live_request_ack", request_id}` and uploads. Sync drops an ack after expires_at. Sync doesn't poll, so a lost notification leaves `delivery` null.
- **Handles.** `dg_` (diagnostic upload) and the `CHK-` diagnostic code are already in `observability/registry/ids.json`, with one implementation in `sdks/typescript/client/src/obs/ids.ts`.

There is no population outside the client: a dialog whose record never arrived is not found, so the client watermark decides coverage. ## 4. Rule conditions

Missing data never yields healthy. Each rule's `decide` gets three-state readings and returns `pass`, a finding (`broken`, `degraded`, or `expected` with its reason code and no module) or `unknown` with a reason; healthy comes only from the kernel, when every planned check passed on complete evidence. The gap column means the check is unknown: either `decide` returns `unknown` with that reason, or a required reading is incomplete, and a finding the rule returns from the other readings still prints. A gap prints as `gap: <code> <party>: <reason>` and makes the header `coverage=partial(report)` or `partial(live)`. "Complete to T" means the source watermark is at or past T. A cause named below goes in the finding's fact text, because a finding line has no cause key. Thresholds are named constants in each rule file, which the rules hash covers: dialog blocked 1000 ms, send settle 15 s, forward pending 60 s, upload request 30 s, upload store 120 s, live ack 10 s, live issue 30 s, live store 60 s, report after leave 24 h. Each rule exports `settle_ms` equal to the longest wait it names after a report or request (150 s for the upload rules), so records still arriving after the Episode ends are read before the check counts as checked.

## 6. Fault scenarios

Samples follow the line grammar in `docs/diagnose.md`. Handles and times are illustrative and `<hash>` is the rules hash; code, Participant, hop and module are exact. The anchor line and the `next:` lines are left out. ## 7. Out of scope and traps

- **Don't touch:** other prefixes, the flight recorder ring or its content, `<ObservedSurface>`, the outbox, `BLIND_SPOT` logic, edge logs, the rate limits (`apps/api/internal/httpapi/problem_reports.go:34` to `:37`), the participant hash, React Native, `renderCrashed`, and production config or secrets (setting the new token hash in production is the lead's step). Flag `docs/observability.md:8` ("not written ... to durable rows") to the lead, since `problem_reports` stores `client_session_id`; don't edit it.
- A 200 `{sent: true}`, a `client.problem_reported` row or a `sent` surface is not proof of storage. They copy the API's decision. Proof is the `report` row.
- The outcome log, the decision and the row are one witness. So are Sync's deliver decision and the row's `delivery` column.
- An upload is `ok` only after `complete` returns `stored`. A resolved PUT `fetch` is not success, and the checker still does its own GET and parse.
- An empty `problem_reports` or `diagnostic_uploads` query from a source that isn't complete is a gap, never "no reports" or "no uploads". A row without `sdk_version` is a gap, not an old client to skip.
- Don't read the dialog's text to get a reason code, and don't put the baggage `session.id` in `client_session_id`.
- Build `state` from named fields. Never serialize the snapshot: no `mediaProof`, Sync token, Authorization header, SDP, description, chat or board content. The description and diagnostics text never reach logs, spans or Axiom.
- Rules live only in `observability/rules/<code>.mjs`, declared in `observability/registry/areas/report.json` and proven by their fixtures in the coverage gate (`scripts/gates/obs-coverage.mjs`). Don't add them to `scripts/diagnose-call/rules.mjs` or `scripts/diagnose-call/reports.mjs`, which belong to the older `diagnose call` report.
- Don't add code to `ChalkSync.Transport.Socket.LiveRequests` (`apps/sync/lib/chalk_sync/transport/socket/live_requests.ex:1`); it handles live targets and directed requests. Introspection goes in the new `ChalkSync.Live.Introspection`.
- Don't wrap every function in `op`, add Sync polling, or add a Discord retry. Never build a CHK code or a handle by hand: `diagnosticCode` and `formatHandle` are the one implementation.
- Don't edit `apps/api/internal/adapters/postgres/tenant_purge_catalog.go`: it purges every table with a `tenant_id` column on its own (`:152`), so the three new tables only need that column.
- Deploy the API before web, because `apps/api/internal/httpapi/problem_reports.go:51` rejects unknown fields, and Sync before the SDK. Follow `apps/api/docs/route-workflow.md` and `apps/api/docs/database-workflow.md`, then run `pnpm run regen`.
