# Slice specs

Each file here is the spec for one vertical slice of the [hyper-observability plan](../../hyper-observability.md) (section 9). A slice adopts the observability kernel in its own modules and owns its area file, symptom codes, rules, fixtures, fault scenarios and CLI lines. The four foundation contracts (C1 IDs and envelope, C2 witnesses and verdict, C3 delivery, C4 CLI output) are implemented, and this page is the contract every slice extends. Where a spec's wording differs from this page, this page and the registry win, and the spec keeps its scope and decisions.

Every symptom code, fact and reason code a slice names starts with one of its prefixes, and the generator rejects any that doesn't. Event and machine names only have to be dotted snake_case and unique across the registry, so an event may name its emitter instead (`sync.episode.ended`, `client.call_ended`) or carry the slice's prefix (`obs.flags_snapshot`). A row an older code path already sends as an `sdk.telemetry` `type` (`render_crashed`, `call_stats`) is declared as a dotted event with a `legacy` match on that type, the way `client.call_ended` is. A slice never defines any name under another slice's prefix and never edits another slice's area file. When a symptom belongs to another slice, the spec names that slice and the builder leaves it alone.

## The rule model: one way to add a check

A check has exactly one home, and [docs/diagnose.md](../../../diagnose.md) ("Add a check") is the step-by-step procedure. The worked example is `end.wrong_screen`: copy its shape.

1. **Facts** go in the area file's `facts`. Each has a `name` under the area's prefix, a `kind` (`once`, `state`, `aggregate` or `event`), a `per` of `seat`, `item` or `any`, and the `events` that witness it. Each event names its `source`, the field the fact compares (`claim`), the `failure_claims` that mean failure and the `fields` a reader needs. A row of a per-seat fact that names no Participant or connection never binds to a seat.
2. **The symptom** goes in the area file's `symptoms`: its `code`, the `item` kind it judges, `per` seat or item, a `doc` and `user_words`, its `witnesses` and its `fault_scenario`. Each witness is `{ fact, from, required, independent, query, doc }`: the fact it reads, the sources that witness it, whether the check needs it, how many independent origins it needs, and the query that reproduces it.
3. **The rule** is `observability/rules/<code>.mjs`. It exports `symptom`, `expected` (one sentence of what a healthy subject produces), `applies(declaration, seat)`, `decide(input)` and, when records keep arriving after the item ends, `settle_ms`. `applies` reads only the declaration, so the plan never depends on what the telemetry contains. `decide` gets a reading of each fact as `present`, `absent` or `unknown`, and returns `pass`, `unknown` with a reason, or a finding with an outcome (`broken`, `degraded` or `expected`), `hop`, `module`, `reason`, `upstream` and facts that cite only rows from its readings. A rule never returns `healthy`: the verdict builds `healthy` from a sealed bundle when every planned check passed.
4. **The fixtures** are `observability/fixtures/<code>/positive.json` and `observability/fixtures/<code>/healthy.json`, each `{ description, asof_ms, declaration, rows }`, with rows shaped like real telemetry (registry envelope and event fields). The coverage gate, `node scripts/gates/obs-coverage.mjs`, judges both through the diagnose kernel with `scripts/diagnose-call/proof/rows.mjs`: the positive fixture must give a finding with the code, and the healthy one must check every eligible subject and give none.
5. **The fault scenario** drives the real code into the symptom and judges what it records the same way (`sdks/typescript/client/src/connection/end-wrong-screen.fault.test.ts`). Once every link exists, the symptom comes off `observability/registry/coverage-allowlist.json`, and the gate fails if it stays there.

A slice never adds a second way to do any of this: no catalogue entry outside the area file, no `evaluate()` rule, no rule-local fixture format and no check the coverage gate can't see. Fields, events, reason codes and state machines follow `observability/registry/README.md` (its steps 2 to 5 and its kernel table).

## Words every spec uses

- **Items and proof profiles.** A check judges one item: an `episode`, an `attempt` (a join that never became an Episode, keyed by its client session `cs_`), a `job`, or one UTC day of a `space`, a `tenant` or the `platform` (one environment). The profile is what the item should have produced, and it is chosen from the authority's declaration alone before any telemetry is read: Postgres for Episodes, seats, jobs, Spaces and Tenants, the API and edge request records for attempts, and the release markers for the platform. So missing evidence can never shrink what an item is judged against. The item kinds are in `observability/registry/core.json` (`items`) and the declarations in `scripts/diagnose-call/proof/profile.mjs`.
- **Verdict fields.** `outcome` is `broken`, `degraded`, `expected`, `healthy` or `unknown`. `coverage` is `complete` or `partial(...)`, with `checked=c/e`; an item with no current verdict reads `unchecked` or `stale`. `disagreement` lists witnesses that contradict each other. They are three separate fields: never fold one into another. `healthy` needs `coverage=complete`, so a sample that shows `healthy` with partial coverage is wrong.
- **Backstops.** `UNEXPLAINED` (a failure or problem report no check explains), `BLIND_SPOT` (a report that arrived after the verdict, or a report stream that could not be read completely), `WITNESS_DISAGREEMENT` (two witnesses contradict). `unchecked` means no verdict exists yet and `stale` that rows or rules changed after it; neither ever reads as healthy. A slice rule never emits a backstop; the kernel does.
- **Readings.** A rule reads each fact as `present`, `absent` (complete coverage proves no such row exists) or `unknown`. A record leaves out a value it doesn't have rather than write `0`, `""` or `"unknown"` for it, so a missing number never looks like a measured zero.
- **Kernel calls.** Every kernel has the same five: `op(name, fields, work, { classify })` with exactly one terminal `ok`, `expected(code)` or `error(code)`; `transition(machine, from, to, trigger, trail, { reason })` at the existing state owner, against a machine declared in the area file; `decision(name, decision, fields, reason)` after the authoritative commit; `surface(name, fields)`, which returns the dismiss call, at committed display; and `fact(name, fields)` for measurements. The TypeScript kernel is `createKernel` in `sdks/typescript/client/src/obs/kernel.ts`, the Go kernel is the `obs` package generated from `observability/kernel/go` into `apps/api/internal/obs` and `features/media/sfu/internal/obs`, and the Elixir kernel is `ChalkSync.Obs` in `apps/sync/lib/chalk_sync/obs.ex`. The per-language signatures are the table in `observability/registry/README.md`. Web and React Native have no shared surface component yet, so the first slice that records a surface adds an `<ObservedSurface>` wrapper to a shared package, and later slices reuse it.
- **IDs.** Display handles come only from `formatHandle(kind, id)` and are parsed only by `parseHandle(text)` in `sdks/typescript/client/src/obs/ids.ts` (Go and Elixir have generated twins). Never build a handle by string concatenation. The kinds and prefixes are in `observability/registry/ids.json`: `ten_` tenant, `spc_` Space, `ep_` Episode, `pt_` Participant seat, `usr_`/`agt_` User or Agent (tenant tokens, printed in full), `dev_` device, `cs_` client session, `jr_` journey, `rq_` request, `tr_`/`sp_` trace and span, `mc_` media connection, `pm_` provider media session, `sc_` Sync connection, `op_` op, `dc_` decision, `rec_` recording, `job_` job, `whd_` webhook delivery, `adm_` admission request, `ev_` event row, `bt_` delivery batch, `f_` finding, `fl_` flag set (`flags_hash`), `dg_` diagnostic upload, `ak_` API key and `wh_` webhook endpoint. `CHK-XXXX` is the code a person reads out from a client; it comes from the client session id and is resolved only within a scope. A new id kind goes into `observability/registry/ids.json` through the foundation lane, so that `formatHandle` and `parseHandle` know it; a slice never invents a local prefix.
- **Delivery (C3).** Every record carries `event_id` and `seq`, and every batch carries `batch_id`, `source_id` and `next_seq` (every seq below it has been assigned). A client's `source_id` is its client session id. A source that stops says `end=closed` (it said its last `next_seq` exactly) or `end=abandoned` (a successor found it dead). A drop record names the seqs it gave up on in `dropped_seqs`, half-open `[from, to)` ranges with at most 64 of them, with a `drop_reason` of `queue_full`, `credential_expired` or `refused`, and `dropped_source_id` when the seqs belong to a predecessor source. An open gap, meaning a source that never closed or a range it never accounted for, makes the seat it covers unchecked, never healthy. The fields are in `observability/registry/envelope.json`.
- **Source binding.** The ledger binds a telemetry source to the first Participant whose batch touches it, as its own source or as a predecessor a drop record names (`apps/api/internal/telemetrydelivery/binding.go`). A later Participant of the same User or Agent, which is what a rejoin produces, is a successor and may write to it. Anyone else is refused with `source_bound`: the whole batch when its own source is bound to someone else, or only the drop record when it names a predecessor it may not write, so the rest of the batch still lands. A guest has no User, so a source bound to a guest has no successors. So a Participant that learns another source's id can't hide that source's gaps.
- **Witness sources.** The sources in `observability/registry/core.json`: `client` (SDK, web or mobile record, per seat), `api` (API request log or decision), `sync` (Sync span or log), `sfu` (Chalk SFU journal or stats), `cf` (Cloudflare Realtime provider response), `recorder`, `lambda`, `provider_webhook`, `db` (a Postgres row read at check time), `r2` (an object or its readback), `host` (worker host or systemd log), `edge` (Cloudflare Worker edge log), `report` (a problem report) and `release` (a CI or deploy-script release marker). Two sources are independent only when neither copies its value from the other. A client event that logs the code the API sent back is the same decision as the API's log, not a second witness.
- **Module names.** A finding's `module=` is `<component>.<area>`, where the component is one of `observability/registry/core.json`'s `fault_components` (`web`, `react`, `rn`, `sdk`, `mobile`, `ios`, `api`, `sync`, `sfu`, `cf`, `recorder`, `dispatcher`, `postgres`, `storage`, `host`, `tenant`) and the area may itself be dotted (`api.webhooks.dispatcher`). `network` and `unknown` stand alone. A module never starts with a symptom prefix, so `db.`, `edge.`, `release.` and the rest never name a module. An `expected` finding has no module.
- **Severity.** `high`: a Participant can't take part (no entry, no media, crash, lost artifact), or something they tried to stop showing stays visible to others (a share that won't stop). `medium`: they take part but something they need is wrong or late (frozen video, recording hours late). `low`: cosmetic, or invisible to Participants but visible to operators. Severity is spec wording for ordering the work; the registry doesn't carry it.

## CLI samples (C4)

Every spec's CLI lines follow the line grammar in [docs/diagnose.md](../../../diagnose.md) ("The line grammar"), and the goldens in `scripts/diagnose-call/golden/` are the shapes to copy. A slice extends those shapes and adds no new ones. The decisions a spec most often gets wrong:

- **Headers** are `episode ep_x tenant=T`, `attempt cs_x tenant=T`, `job job_x tenant=T`, `space spc_x 2026-11-18`, `tenant ten_x 2026-11-18` and `platform production 2026-11-18`, then `outcome=`, `coverage=`, `checked=`, `asof=` and `rules=` (the 8-hex rules hash). `day T 2026-11-18` sweeps a tenant's Episodes, attempts and jobs over its local day. Spec samples leave out line 2, the anchor; the real output has it.
- **Findings** are `f_x <outcome> <code> <party> <when>`, then `hop=`, `module=`, `upstream=witnessed|unknown` and `ev=ev_x` when they apply. The outcome is always the second word. An `expected` finding has no `module=` and names its reason code in `reason=`, as in `f_d2a1 expected end.time_limit all +60:00 reason=end.time_limit ev=ev_0b9e`. Slice detail never goes on the finding line as extra keys: it goes in a `fact:` line, a related record or the `evidence` view.
- **When** in an Episode, attempt or job view is relative to the item's start (`+mm:ss`, minutes may pass 59, negative before the start, a range as `+07:10..+10:40`). A Space, Tenant or platform day prints the UTC `HH:MM`, because its header names the UTC date, so a finding at 10:00 UTC on a Tenant day prints `10:00` and a time on another day prints `MM-DD HH:MM`. The `day` sweep prints the tenant-local `HH:MM`, and the views that span days (`check`, `participant`, `pattern`) print the local `MM-DD HH:MM`.
- **Parties** are bare handles with an optional name: `pt_4c1e(Haris)`, `usr_th-1041(Haris)` or `all`. There is no `scope=` key.
- **`fact:`** brackets hold only `ev_` handles, or `[proven absent]` when complete coverage proves no such row exists. They never hold a source name. What was expected, what was observed, the witnesses, watermarks, queries and falsifiers print in `diagnose evidence f_x`, not on the fact line.
- **Coverage** is `complete` or `partial(<names>)`, comma-separated with no spaces and sorted. Each name is the symptom prefix of a check that could not decide (`partial(board)`), or `open` (the item has not ended), `unbound` (a row whose identity doesn't match the authority) or `empty` (the profile planned no check). Every name has a `gap:` line, such as `gap: board.view_jumped all 4 seats: board.camera not emitted by client 3.1.0` or `gap: open: the job has not ended, so what it has not done yet is unknown`.
- **Group lines** in sweeps are `<code> <outcome> <kind>s=<n>` with `people=<n>` and the first handles: `admission.unresolved broken attempts=1 cs_6d5e`.
- **Related records** a slice shows are `<kind> <handle> key=value`, such as `upload dg_3f9a readback=ok`, where the handle is one of the registry's id kinds.
- A `hypothesis:` prints only when an upstream witness supports it, with what would falsify it. `upstream=unknown` means the evidence stops at that hop, so a spec never names a cause past it.

## Recipe for a builder

Do these in order. Each step ends in a check; don't start the next until it passes.

1. **Read the spec twice, then the plan sections it cites.** Open every file:line in the spec. If a line moved, find the same code by name and use the new line. If the code is gone, stop and report it; don't guess a replacement. A path written as `path (new)` is a file your slice adds.
2. **Declare the facts and symptoms** in your area file as the rule model above says, with any new fields (each with `sensitivity: null`), events, reason codes and machines as `observability/registry/README.md` says. Run `pnpm run regen`, then `pnpm run check:generated`.
3. **Adopt the kernel at the boundaries in section 5 of your spec, and only there.** Use the call the spec names. Keep the existing log line or metric next to it unless the spec says to remove it. A catch you add either rethrows or reports through the kernel.
4. **Write one rule per symptom** at `observability/rules/<code>.mjs`. Where the spec says "unknown", `decide` returns `unknown` with a reason that names the missing evidence, never `pass`.
5. **Write the positive and healthy fixtures** and the fault scenario, then take the symptom off `observability/registry/coverage-allowlist.json` and run `node scripts/gates/obs-coverage.mjs`. Build fixture rows from the real event shapes, not from the rule's own expectations, and give the healthy fixture the near misses the rule must not fire on.
6. **Wire the evidence into the example world.** Add each fact to the `emits` of the watermark that delivers it in `scripts/diagnose-call/fixtures/nov18.mjs`, with observations, or every item the check applies to reads as unknown. Rewrite the goldens with `DIAGNOSE_GOLDEN=write node --test scripts/diagnose-call/output/output.test.mjs` and check that every line you print matches your spec's fault table.
7. **Run each fault scenario in section 6** on the real stack (local dev stack or an Orb, as the scenario says). Save the `diagnose` output next to the scenario. Then run the healthy control and save its output too. If the environment a scenario needs doesn't exist, stop and report it; never stand in a fixture for a real run.
8. **Run the gates** for the files you touched (see `scripts/gates/README.md`); heavy ones go to Instabox per AGENTS.md.

## Done bar

A slice is done only when all of these hold:

- Every injected fault in section 6 is diagnosed with the right symptom code, the right party (a Participant, or the item when the spec says `all`) and the right module, with the CLI line the spec gives. Close is not done: a different code, the wrong Participant or `UNEXPLAINED` is a failure.
- Every healthy control raises no finding and no backstop, and its coverage is `complete` or names exactly the gaps the spec expects.
- Removing any required witness's rows from the healthy fixture leaves that subject `unknown`, never `healthy`, and deleting evidence never erases a `broken` finding another witness already proved. The metamorphic tests in `scripts/diagnose-call/proof/soundness.test.mjs` check this over the example world.
- `pnpm run check:generated` and `node scripts/gates/obs-coverage.mjs` pass, every new symptom is off the coverage allowlist, and the coverage graph lists it with its witnesses, rule, both fixtures and fault scenario.
- Nothing outside the slice's section 1 files changed, except its area file, its rules and fixtures, the example world and goldens, and its CLI lines.
