# Chalk web

This Vite, React 19, and TanStack Router app serves three roles:

- the public marketing shell at `/`;
- a production-capable public-SDK consumer Space at `/space`;
- a compact public-surface preview at `/sdk-preview`.

It is not a complete hosted real-time product. `/new`, `/whiteboard`, and `/status` are blank routes. `/privacy` and `/terms` are public legal pages. Track the remaining gaps in the root [`checklist.md`](../../checklist.md).

Routes live in `src/routes/` and are generated by TanStack Router. Shared product behavior belongs in the SDK packages; this app remains a thin first-party integration and verification surface.

## SDK Space

The `/space` route uses `createChalkPublicClient` from the TypeScript SDK. The index route collects a display name, creates a public Space, and replaces the URL with the verified `invite_link` as `/space/{slug}#spaceInviteToken=...`. A named route sends that capability token to `arriveBySpacePublicInvite`.

An arrival can be admitted immediately or return `pending`. Pending arrivals poll `getSpacePublicInviteArrival` until they are admitted, and Cancel calls `leaveSpacePublicInviteArrival`. The browser client includes its cookie on every request, refreshes media access through `refreshSpacePublicInviteAccess`, and releases the arrival when the Participant leaves or the page unloads.

`pnpm --dir apps/web dev` binds Vite to `127.0.0.1:3070` and proxies `/v1` to `http://127.0.0.1:8080` by default. Set `CHALK_DEV_API_ORIGIN` to use another API origin. Production builds set `VITE_API_URL` to the public API origin.

Browser journey telemetry is opt-in through `VITE_CHALK_TELEMETRY_ENABLED=true` and the same journey context is passed to the public SDK and Chalk client.

## Commands

Run commands from the repository root:

```bash
pnpm --dir apps/web dev
pnpm --dir apps/web test
pnpm --dir apps/web check-types
pnpm --dir apps/web build
```

## Web release

The shared release runner builds the web app once, uploads that same
`dist/client` artifact to staging, verifies it, then uploads and verifies
production. It requires an exact 40-character commit SHA and a clean detached
checkout. The local command creates that checkout automatically, so unrelated
work in the shared repository cannot enter a release. Staging is the default
safety gate; use `--skip-staging` only for an explicitly approved fast
production repair.

For a local release, keep the Cloudflare credentials in a 1Password-backed
environment file (the file contains `op://...` references, never secret
values), then let `op run` inject them for one process:

```bash
# .private/chalk-web-release.env (untracked; use your vault item references)
# CLOUDFLARE_API_TOKEN=op://dev/<cloudflare-item>/api-token
# CLOUDFLARE_ACCOUNT_ID=op://dev/<cloudflare-item>/account-id
op run --env-file=.private/chalk-web-release.env -- pnpm run release:web
```

Use `--dry-run` to inspect the preflight and command plan without building,
uploading, or verifying anything:

```bash
pnpm run release:web -- --dry-run
```

If the prior local release was force-killed and left its lock behind, recover
it only after checking that no release process is still running:

```bash
op run --env-file=.private/chalk-web-release.env -- pnpm run release:web -- --recover-stale-lock
```

The runner reads the recorded owner PID and refuses to remove a live lock.

CI should inject `CLOUDFLARE_API_TOKEN` from its encrypted secret store and
call the CI alias with the workflow SHA:

```bash
pnpm run release:web:ci -- --sha "$GITHUB_SHA"
```

The runner requires Node 22 or newer, pins pnpm and Wrangler, installs from the
local pnpm store when possible, and uses Turbo's build cache. It passes the full
SHA into the build metadata and service worker and always invokes the existing
deployment verifier after each upload.

Local releases run from a detached checkout but keep the persistent Turbo cache
in the main checkout at `.turbo/cache`. Set `CHALK_WEB_TURBO_CACHE_DIR` to a
different path inside the main checkout when needed; relative paths resolve from
that checkout. The release runner passes this absolute path through Turbo's
`--cache-dir` option, so no cache symlink is created. Dependency package builds
can be reused across release SHAs, while the web build still includes its exact
SHA and release configuration in its cache key. CI restores the same
`.turbo/cache` path before the release build.
