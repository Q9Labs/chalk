# end.wrong_screen fixtures

The positive and healthy fixtures are not written by hand. They are the rows the real emitters produce for the symptom's fault scenario and its healthy control, carried from hop to hop through the hand-off files in `chain/`. Each hop is a test that drives real code, and each one compares what it produced with the committed file, so a hop that renames a field, drops one or changes a value fails its own test.

1. Hop (a), `sdks/typescript/client/src/connection/end-wrong-screen.fault.test.ts`, drives the real client, connection, kernel and outbox. In the positive run the end notice is lost and the status read is stale, so the client records `client.call_ended` with `connection_lost`; in the healthy control it records an Episode-ended reason. It writes the ledger frames the outbox posts to `chain/client-frames.<run>.json`.
2. Hop (b), `TestTelemetryChainEndWrongScreen` in `apps/api/internal/httpapi/telemetry_chain_test.go`, posts those frames to the real telemetry route with a real credential and the memory ledger. It checks that every field the client sent reaches the logged row unchanged and that every row field is a registry field, then writes the rows to `chain/api-rows.<run>.json` and the ledger's report of the Episode, in the shape `telemetry-watermarks` prints, to `chain/ledger.<run>.json`.
3. Hop (c), `apps/sync/test/chalk_sync/obs_chain_test.exs`, ends a real Episode on Postgres at its maximum duration. The finalizer reads the reason back from `episodes.end_reason` and records `sync.episode.ended` through the production emitter, and the log subscriber's row goes to `chain/sync-rows.json`.
4. Hop (d), `scripts/diagnose-call/proof/end-wrong-screen-chain.test.mjs`, joins Sync's row and the API's rows into `positive.json` and `healthy.json` and judges them through the row adapter and the kernel. The positive fixture gives the finding and the healthy one checks its seat and gives none. It also reads the same rows and the ledger report through the live reader, as `diagnose --live` would: the positive run gives the finding, cited from the client session the frames carry, but the healthy run stays unchecked, because Sync has no delivery ledger and the ledger misses the client's records before the last frame. So a healthy live verdict for this symptom is unchecked, never healthy, until Sync has a ledger.

`chain/hops.json` declares each hop's test, its command and the files it writes. Each fixture lists its hand-off files under `chain`, and `node scripts/gates/obs-coverage.mjs` fails when a fixture's rows are not exactly those files' rows, when the first hop is not the fault scenario, or when a file in `chain/` or a fixture is written by no hop.

The ids, clocks and receipt times are pinned, so the hops write the same files on every run; only the registry hash (`schema_ver`) is left out of hop (c)'s comparison, because any registry edit changes it. `node scripts/gates/obs-chain-replay.mjs end.wrong_screen` runs the hops in order in write mode and fails when any of them writes a file that differs from the committed one, skips, or fails. To rewrite the files after a deliberate change, run each hop's command from `chain/hops.json` with `CHALK_CHAIN_WRITE=1` in order, then format them with `pnpm exec oxfmt observability/fixtures/end.wrong_screen`. The hops compare parsed JSON, so formatting is only for the format gate.
